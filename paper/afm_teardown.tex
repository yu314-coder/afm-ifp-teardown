\title[Apple's On-Device Foundation Model, Rebuilt]{Apple's On-Device Foundation Model, Rebuilt:\\
A Complete From-Weights Reconstruction of \code{afmplus-v11.2-ifp}\\ (AFM~3 Core Advanced) and a Portable llama.cpp Runtime}
\author{Yu Yao-Hsing}
\email{euler.yu@gmail.com}
\date{November 9, 2026}

\begin{abstract}
We reconstruct Apple's current on-device foundation language model---asset \code{com.apple.fm.language.instruct\_3b.base.generic\_sparse}, display version \code{afmplus-v11.2-ifp}, the model Apple calls \emph{AFM~3 Core Advanced}---entirely from the files Apple Intelligence installs on a Mac, and run it in llama.cpp on any operating system. The model is a 56-layer, 20.3-billion-parameter transformer with a 1536-wide residual stream, 16 query and 8 key/value heads, KV-cache sharing across its last 21 layers, an unusual post-normalised (``x/y'') residual with four learned RMSNorm gains per layer, and an Instruction-Following-Pruned sparse feed-forward network: 23 always-on experts plus 23 of 348 routed experts per token, chosen by a separate router network evaluated once at layer~12. Every 2-bit weight is carried into GGUF \emph{bit-exactly} (55 million spot-checked weights, zero differences); the tokenizer reproduces Apple's own token counts on 81/81 test texts. The two things the model files do not contain---the prompt template and the rule that picks experts---we read out of Apple's inference frameworks: the conversation is rendered as a system turn plus a separate developer turn, and the experts for a whole prompt are chosen from the last prompt token's hidden state and re-chosen every 32 positions. Both are confirmed by Apple's public token counter and by Apple's own runtime log. Against Apple's live model at temperature zero, the reconstruction's next-token choice agrees with Apple's on \textbf{97.0\%} of answer tokens (95.3\% on a harder 230-prompt set), and 17 of 40 free-running answers are identical to Apple's character for character. The last five points came late. llama.cpp applied the embedding scale twice (Apple applies none), Apple adds the layer-0 input bias only to generated tokens, and the Neural Engine's SiLU is a 33-knot piecewise-linear table that we now reproduce. Nothing in the model is trained or fitted. We also decode the 26 Apple Intelligence feature adapters (rank-48 LoRAs), Apple's 9M-parameter speculative-decoding draft model, with which speculation in llama.cpp is lossless, and the 358M-parameter image encoder, which matches Apple's own encoder run on the Neural Engine (cosine 0.96--0.99): through it the reconstruction predicts Apple's image captions 94.0\% of the time teacher-forced, as well as with Apple's own encoder, and 5 of 13 free-running captions are identical to Apple's. Finally we decode Apple's 300M base model (\code{afmplus-v11.0-pico}) and the adapters built on it: with its default adapter it reaches a perplexity of 21--31 on plain English, Apple's safety guard, run through llama.cpp, answers \code{safe} for benign text and labels harmful text in its own category format, and through the 300M model's own image encoder its people counter is right on 9 of 10 photos.

For most of this project the assembled model predicted nothing. The cause was a single misaligned read: every normalisation gain was taken one element early. We found it with probes \emph{calibrated} on a healthy Apple model---Xcode's on-device code model, whose MPSGraph package we dumped to readable MLIR, executed on the GPU from our own process and reproduced exactly in NumPy. The report documents the model's full structure, the storage formats, the debugging instruments and their calibration, the prompt template and expert schedule recovered from Apple's runtime, the llama.cpp implementation, a standalone converter, every negative result, and what still separates the port from 100\%.
\end{abstract}

\section{Which model is this?}\label{sec:which}

\subsection{The layer: a post-normalised ``x/y'' residual}

Each layer carries four learned RMSNorm gains $g_0,\dots,g_3\in\mathbb{R}^{1536}$. Unlike a pre-norm transformer, both residual additions add \emph{normalised} values:
\begin{align*}
x_L &= \mathrm{rms}(h_{L-1})\odot g_3^{L-1}\qquad(\text{layer 0: } x_0 = k\,e_t + b,\ \text{no norm})\\
h'_L &= x_L + \mathrm{rms}\big(\mathrm{Attn}_L(x_L)\big)\odot g_0^{L}\\
y_L &= \mathrm{rms}(h'_L)\odot g_1^{L}\\
h_L &= y_L + \mathrm{rms}\big(\mathrm{FFN}_L(y_L)\big)\odot g_2^{L}
\end{align*}
with $\mathrm{rms}(v)=v/\sqrt{\mathrm{mean}(v^2)+\varepsilon}$, gains used literally (no $1+g$), and a final output $\mathrm{rms}(\mathrm{rms}(h_{55})\odot g_3^{55})\odot g_\mathrm{out}$ multiplied by the tied embedding. The residual wiring was read from the DMA pattern of the ANE program: the normalised attention input is written to DRAM scratch and read back by the attention residual add; the FFN residual add reads the normalised FFN input. Only this wiring reproduces Apple's outputs (standard residual: 0\% top-1).

\subsection{The Instruction-Following-Pruned feed-forward network}

Sparse layers add two SwiGLU blocks without any gating weights:
\[
\mathrm{FFN}(y)=\underbrace{\sum_{e=0}^{22}\mathrm{SwiGLU}_e(y)}_{\text{always on}}\;+\;\underbrace{\sum_{e\in\mathcal{S}(y)}\mathrm{SwiGLU}_e(y)}_{|\mathcal{S}|=23\text{ routed}},\qquad
\mathrm{SwiGLU}_e(y)=W^{\mathrm{down}}_e\big(\mathrm{SiLU}(W^{\mathrm{gate}}_e y)\odot W^{\mathrm{up}}_e y\big),
\]
each expert being $256$ wide. The ANE program runs the always-on experts from static kernels and the routed experts from a mutable kernel patched at runtime from \code{ifp\_rasterized\_weights.bin}. Both halves matter: the always-on experts alone reach 62.9\% top-1, the routed experts alone 1.4\%, both together 87.5\% (measured with the earlier template).

\paragraph{When experts are chosen.} Apple's runtime does not route per token. It runs the dense layers over the whole prompt, takes the layer-12 input of the \emph{last} prompt token, runs the router once, and uses that expert set for every prompt token and for generation; it re-picks from the current token only at absolute positions that are multiples of 32. Section~\ref{sec:runtime} shows how this was read out of Apple's inference framework.

Experts in \code{ifp\_rasterized\_weights.bin} use the same codes with a simpler order: code $p\mapsto$ (row $16\lfloor p/(16\,\mathrm{in})\rfloor + p\bmod 16$, input $\lfloor p/16\rfloor \bmod \mathrm{in}$).}\label{fig:tile}
\end{figure}

\paragraph{Exact GGUF encoding.} llama.cpp's Q2\_K stores, per 256 weights, sixteen 4-bit sub-block scales $\mathit{sc}$ and mins $m$, a super-scale $d$ and super-min $d_{\min}$, and evaluates $w = d\,\mathit{sc}\,c - d_{\min}\,m$. Choosing $\mathit{sc}=2$, $m=3$ and $d=d_{\min}=s/2$ gives
\[
w = \tfrac{s}{2}\cdot2c-\tfrac{s}{2}\cdot3 = s\,(c-1.5),
\]
and halving an fp16 number is exact (barring underflow, which never occurs here). The int4 embedding ($w=s_t\,q$, $q\in[-7,7]$, per-token fp16 scale $s_t$) maps exactly onto Q4\_0 with $d=s_t$ and nibble $q+8$. Dequantising the GGUF with gguf-py reproduces Apple's weights with maximum absolute difference 0.

\paragraph{Layout facts and how they were ground-truthed.} We compiled known weights through Apple's own ANE compiler (\code{mil\_to\_hwx -a h16}) and decoded the result: the output axis is the bank-cyclic stripe above, the input axis is natural, the codebook and row scales are as in Figure~\ref{fig:tile}, and constants (gains, biases) are stored in natural order. A calibrated copy-circuit probe (Section~\ref{sec:validate}) independently confirms the stripe, the head order and the V/O pairing: every alternative layout scores at chance.

\begin{finding}
The earlier parse located the table by statistical signatures and accepted a start two bytes early. Every RMSNorm therefore multiplied channel $r$ by the gain of channel $r{-}1$. Because $g_0$ and $g_2$ are zero-centred, this flipped the sign of about a third of every residual write at every layer, and the assembled model predicted nothing (0\% top-1, no induction).
\end{finding}

\paragraph{How it was found.} Nothing looked wrong in isolation: each tensor was correctly laid out and correctly paired. The breakthrough was calibrating probes on a healthy Apple model and then comparing \emph{reader--reader} with \emph{reader--writer} relations. In AFM, query--key and gate--up relations were as healthy as in CodeLM, but value--output (copy heads) and up--down (FFN neuron coupling) relations were weak. In a trained network, the sign of the coupling between up-row $i$ and down-column $i$ agrees with the sign of the gain that scales the write. In AFM the \emph{number} of negatively coupled channels equalled the number of negative entries of $g_2$ in every layer---while their \emph{positions} disagreed (Figure~\ref{fig:offbyone}, left). Matching each channel's 11-layer sign signature against the table gave a constant offset of one element. Read aligned, the agreement rises to 98--99.9\% (right) and the model works: 66\% top-1 against Apple's outputs on the first attempt, rising to 87.5\% with the llama.cpp port and exact tokenization.

\section{Validation instruments and their calibration}\label{sec:validate}
%======================================================================

\paragraph{The oracle.} \code{afm -t 0} (a small Swift wrapper around the Foundation Models API) produces Apple's greedy answers; at temperature zero, Apple's top-1 token at every answer position is the next token, so teacher-forced top-1 agreement is an absolute measure. We use 40 prompts (1127 answer tokens). The API exposes no probabilities.

\paragraph{A healthy reference: CodeLM v3.} Xcode's on-device code model ships as a GPU MPSGraph package. Its MLIR (via \code{-getIR}) is a complete, readable tamm transformer---pre-norm, standard residual, RoPE then QK-norm, SwiGLU, KV reuse from layer 34, int4 weights with group-32 scales---with the same backbone shape as Apple's other 3B-class models (56 layers, 35 KV-owning, 2048 wide, 16/2 heads). We ran it on the GPU from our own process through \code{MPSGraphExecutable} (100\% induction accuracy) and reproduced its logits in NumPy exactly (correlation 1.00000, 100\% argmax agreement). Its tokenizer and embeddings are unrelated to v7-3b's, so it cannot donate weights---but it calibrates instruments.

\paragraph{What the calibration showed.}
\begin{itemize}
\item \emph{Zero-centred literal gains are normal} in tamm (CodeLM's pre-attention gain: mean $+0.003$, 46\% negative).
\item \emph{The embedding--weight ``alignment ratio'' used for months is not diagnostic}: a healthy model scores the same (1.0--1.4).
\item \emph{The OV copy probe is diagnostic}: CodeLM has several heads that map a token to itself at rank 0--16, even after naive 2-bit rounding; decoded AFM had none below rank 1000 (Figure~\ref{fig:copy}). Every alternative V/O layout scored at chance, which ruled out layout errors and pointed at the gains.
\item \emph{The same-token QK probe} found AFM's query--key circuits healthy (rank-0 heads) and confirmed the head pairing $h\mapsto\lfloor h/2\rfloor$.
\end{itemize}

\section{What Apple's runtime does: the prompt and the expert schedule}\label{sec:runtime}
%======================================================================

Two things the model files do not contain decide what the model sees and which experts it uses: the prompt template (the metadata only names it, \code{afm\_cider\_v2}) and the rule for choosing experts. Both live in code, in two private frameworks of the dyld shared cache: \code{TokenGenerationCore} renders and tokenizes prompts, \code{TokenGenerationInference} drives the model. \code{dyld\_info -disassemble} prints both with Swift symbol names. One detail matters for reading them: Swift stores string literals of up to 15 bytes inside the instruction stream (\code{mov}/\code{movk} immediates), so \code{<start\_of\_turn>} and friends never show up in a strings dump.

\subsection{The prompt template}
\code{PromptPreprocessingTemplateAfmCiderV2Convention} takes its special-token table from the older Cider~v1 convention and overrides only audio and reasoning entries. Decoding the immediates gives turn start \code{<start\_of\_turn>}, turn end \code{<end\_of\_turn>}, and roles \code{system\textbackslash n}, \code{developer\textbackslash n}, \code{user\textbackslash n}, \code{model\textbackslash n}; the ``thought budget: none'' and ``developer static instructions'' entries are empty. Its \code{cacheableSystemPrefix} concatenates
turnStart, the system role with Apple's default instructions, the thought budget, turnEnd, a newline, then turnStart and the developer role. A FoundationModels conversation therefore renders as
\begin{center}\small
\code{<bos><start\_of\_turn>system\textbackslash n}\emph{default}\code{<end\_of\_turn>\textbackslash n}\\
\code{<start\_of\_turn>developer\textbackslash n}\emph{instructions}\code{\textbackslash n<end\_of\_turn>\textbackslash n}\\
\code{<start\_of\_turn>user\textbackslash n}\emph{prompt}\code{<end\_of\_turn>\textbackslash n<start\_of\_turn>model\textbackslash n}
\end{center}
where \emph{default} is the \code{systemInstructions.default} text of the adapter metadata (``A conversation between a user and a helpful assistant. You are a foundation model developed by Apple. \ldots'') and the developer turn holds the app's instructions. The public API verifies every detail: \code{SystemLanguageModel.tokenCount(for:)} accepts transcript entries and returns the length of the rendered prompt, which equals the length the inference service logs (``asked to run 71 tokens'') for the same conversation. Table~\ref{tab:tc} compares it with our rendering. Our earlier template folded everything into one system turn and omitted the instructions our reference CLI passes; with the exact template, teacher-forced agreement rose from 87.5\% to 90.5\% and the first answer token from 30 to 38 of 40.

\subsection{The expert schedule}
The inference log of a single request already shows the shape of the algorithm: a ``prompt expert compute function'' (\code{lora\_48\_ifp3\_r48\_prompt\_opt\_dense\_only\_256\_64}, the dense layers only) runs over all prompt tokens, then ``Picking IFP experts at position=70 isPromptPick=true'' for a 71-token prompt, then the sparse layers run over the \emph{whole} prompt again with the picked experts. The dense-only function returns a \code{1536}$\times$\code{64} fp16 tensor per 64-token chunk, one column per token. In \code{TokenGenerationInference}, \code{computePromptExpertState} builds the router input with \code{IFPDenseLayerOutput.makeExpertsTensor(tokenIndex:)}, whose loop copies the 1536 values of a single column into a $1536\times1$ tensor---no mean, no accumulation. The router (\code{project\_experts}, the network of Figure~\ref{fig:ifp}) then yields the top-23 experts per sparse layer. During generation, \code{repickExpertsAtBoundary} calls the same picker, and \code{IFPExpertPicker} rejects any intermediate pick whose position is not a multiple of \code{expert\_selection\_frequency} (an \code{sdiv}/\code{msub} remainder test against 32). With prompt length $P$, token $t$ therefore uses the experts chosen from $x_{12}$ at
\[
s(t)=\max\!\big(P-1,\;32\lfloor t/32\rfloor\big),
\]
so every prompt token uses the last prompt token's choice. Averaging the prompt instead is clearly wrong (79.3\% teacher-forced), while the single-token rule beats per-token routing (Section~\ref{sec:fidelity}).

\paragraph{An outside check of the router.} Each pick also logs \code{CacheExpertExpertCache: \ldots\ replaced=}$n$, the number of (layer, expert) choices that changed. We ran six long generations on Apple's model, collected its 47 re-picks, replayed the same token sequences through our model and counted how many of our choices change at the same positions. With the single-token rule on the layer-12 attention input the two series agree closely (Figure~\ref{fig:repick}: mean 26.7 versus 27.1 experts, correlation 0.84); prefix means correlate at 0.21--0.53 and the FFN-input variant changes three times too many. This validates the router input, the router network and the rule independently of any answer text.

\section{The llama.cpp implementation}\label{sec:llama}
%======================================================================

The fork adds one architecture, \code{afm}, in \code{src/models/afm.cpp} (about 180 lines), plus three supporting changes.
\begin{itemize}
\item \textbf{Graph.} Layer 0 takes the dequantised embedding row as is (no multiplier) and, for generated tokens other than re-pick tokens, adds the input bias (Section~\ref{sec:fidelity}); each later layer normalises the previous output with $g_3$; queries and keys use \code{rms\_norm}, NEOX RoPE, then a gain multiply; the residuals follow Figure~\ref{fig:layer}. Sparse layers run the always-on experts as a ``shared expert'' SwiGLU of width 5888 and the routed experts with \code{mul\_mat\_id}, summed by one row reduction with no weights. The router network lives on layer 12 and its logits are sliced per layer. The output applies the double norm and the tied embedding.
\item \textbf{KV reuse.} Layers 35--55 call attention with null K/V, and the cache maps them to layer 34. This needed a two-line fix in the non-sliding-window attention path, which assumed K/V were always present.
\item \textbf{Metal kernels.} Metal's batched expert matmul is instantiated for specific experts-per-token counts; we added 14 and 23 (ifp2, ifp3). CUDA uses a generic path for such counts, and Vulkan supports Q2\_K expert matmuls, so no change is needed there.
\item \textbf{Apple's expert schedule.} The router's logits for each sequence persist in a small device buffer (64 sequence slots) owned by the model. A custom graph input computes, per micro-batch on the host, which logits every token uses: a run of several tokens of one sequence is a prompt chunk and takes its last token's logits, which are stored; a single decode token re-picks only when its position is a multiple of 32 and otherwise reads the stored choice. Because the indices are data rather than graph structure, llama.cpp's graph reuse and multi-sequence batching stay correct. Speculative verify batches are handled as single decode tokens, with two position-tagged picks per sequence so that rejected draft tokens leave no trace (Section~\ref{sec:draft}). \code{AFM\_ROUTE\_TOKEN=1} restores per-token routing.
\item \textbf{The embedding-scale pitfall.} llama.cpp's generic \code{build\_inp\_embd()} multiplies by the GGUF's \code{embedding\_scale} (a Granite feature). The first release also multiplied in the AFM graph, so a GGUF carrying our fitted 10 ran at 100. The loader now ignores the key, so old GGUFs run correctly.
\item \textbf{The Neural Engine SiLU.} The activation is the ANE's piecewise-linear table, built from standard ggml operations: a clamp, a magic-constant floor, two 38-entry \code{get\_rows} tables and a relu for the right tail, then rounded to fp16. It costs about 45\% of prompt speed and 20\% of generation speed on Metal; \code{AFM\_EXACT\_SILU=1} switches back to the exact function.
\item \textbf{Router on the CPU.} The router's top-23 margins (median 0.003) are close to the error of Metal's tiled matmul ($8\cdot10^{-5}$ against $2\cdot10^{-7}$ on the CPU; 0.002 expert swaps per layer-pick). Its weights are therefore placed on the CPU, which makes picks identical across backends. The routing state and SiLU tables stay on the layer's device. Agreement is unchanged within noise.
\item \textbf{int8 KV emulation.} The GGUF carries Apple's per-layer K/V scales; keys and values are rounded and saturated to int8 before caching. Rounding uses the fp32 magic constant $1.5\cdot2^{23}$, because \code{ggml\_round} misbehaved on Metal.
\end{itemize}
On an M4 the model processes prompts at about 150 tokens/s and generates 12--21 tokens/s. The patch applies to upstream llama.cpp (commit \code{41ea261}); the repository's workflow builds Windows (CPU, Vulkan, CUDA), Linux (CPU, Vulkan) and macOS (Metal) binaries from it.

\section{Apple Intelligence feature adapters}\label{sec:adapters}
%======================================================================

Apple Intelligence features ship as rank-48 LoRA adapters for this backbone: 26 on our Mac, covering summaries, proofreading, mail replies, smart replies, translation, message actions, reminders, Image Playground suggestions, Photos memories, dictation and others. Each asset holds \code{lora\_i}$N$\code{\_r48\_48\_constant\_data.bin}, where $N$ is the IFP level the feature runs at. Its metadata holds Apple's prompts for the feature (system instructions and content templates, in the \code{afm\_cider\_v2} format) and the same backbone signature as the base model. All of them carry the empty-input SHA-256 as their ``adapter signature'', so that field says nothing about whether an adapter is trained. The FM API's own adapter is untrained (B RMS $3\cdot10^{-5}$), while the feature adapters are trained (B RMS $2\cdot10^{-3}$ to $3\cdot10^{-2}$).

\paragraph{Layout.} A file holds 218 (A, B) pairs as fp16, in segment order: dense (o, q, k, v, \code{linear\_0}, \code{linear\_1}, down) $\times12$, then kv-reuse (o, q) $\times21$, then standard sparse (o, q, k, v) $\times23$. The pairs account for every byte. We chose the orientation, row order, gate/up assignment and scale with a likelihood test. For eight proofreading pairs of our own, the cost of the correct output under the proofreading adapter at ifp2 is 0.016 nats per token with A as $[48,\text{in}]$, B as $[\text{out},48]$, natural row order, \code{linear\_0} = up and scale 1. It is 0.119 with no adapter, and at least 0.036 with any of the other 15 layouts. Scales 0.75 and 1.25 give 0.050 and 0.330.

\paragraph{IFP levels.} ifp1 and ifp2 use the first 5 and 14 always-on experts plus as many routed ones. In llama.cpp these are views of the shared FFN; at 256-aligned offsets they are whole Q2\_K blocks. The level is read from the active adapter (\code{adapter.afm.ifp}). With Apple's prompts, the proofreading, Catch-Up summary and mail-reply adapters produce the expected outputs, and the proofreading adapter fixes tense errors the base model leaves in.

\section{The speculative-decoding draft model}\label{sec:draft}

Apple pairs the model with a small draft model for speculative decoding: asset \code{fm\_api\_generic.draft}, \code{model\_config} \code{v11-ifp-9m}. Its metadata asks for 7 draft tokens per step, exact matching (\code{draft\_soft\_match\_tolerance} 0) and no adaptive length. The asset has no weights file: everything is inside its Neural Engine program (\code{binary\_0.hwx}, 22 procedures: 3 readouts of 8/16/64 tokens and 19 \code{extend} variants) and its \code{program.odix}.

\paragraph{Reading the dataflow.} The 132 weight convolutions (11 per layer) are the tasks with Neural Engine opcode \code{0x46} and a kernel offset. Their roles follow from the surrounding tasks. In layers 1--11 the first 128-channel projection is written straight to the cache by a tile-destination DMA, so it is $V$. The second passes through RoPE, a 32-wide RMS reduction and a gain multiply before its cache write, so it is $K$. Layer 0 orders them $q, k, v$. The attention score scale $1/\sqrt{32}$ sits in the QK matmul's output-scale register, and the softmax is an exp2 with a $\log_2 e$ prescale. The 768-wide FFN hidden is laid out by L2 address: the three up and three gate tiles are written to descending addresses, so the hidden is $[\text{tile}_2 \mid \text{tile}_1 \mid \text{tile}_0]$. In the last layer the compiler re-banks these buffers and leaves one destination register implicit, so we use the conv order there. Norm gains come from \code{\_\_TEXT,\_\_const}, one 0x4000-byte block per procedure, addressed by the tile-source offsets. In layer 2 the query gain multiply reuses the tile the key gain loaded; the compiler had merged the two. The query and key gains of a layer agree up to sign flips inside rotation pairs and a few ulps, so the norm cannot be moved before RoPE. The final norm computes $\mathrm{rsqrt}(\mathrm{mean}((0.1x)^2)+1.19\cdot10^{-7})\cdot0.1$, an fp16 overflow guard equivalent to $\epsilon=1.19\cdot10^{-5}$.

\paragraph{Validation.} A NumPy forward of this description predicts Apple's own next answer token (from the 3B model, teacher-forced) 42.95\% of the time on the 40 prompts (1127 tokens) and 37.7\% on the 230 (6572 tokens). Every alternative we tried collapses: cyclic instead of unit-blocked output rows 0.0\%, reversed RoPE direction 16.7\%, query head $h\to$ KV head $h \bmod 4$ 6.7\%, $K$ and $V$ swapped 1.5\%, FFN tiles in conv order 2.3\%, raw codes without $s$ 0.3\%. The input scale is a sharp optimum at 1 (0.25: 27.6\%, 4: 36.5\%). The ANE SiLU table changes nothing (42.95\% either way). Simulating Apple's speculation (7 tokens, exact match), the draft's proposals are accepted 0.61 tokens per step on the 230 prompts, so each target call yields 1.61 tokens.

\paragraph{In llama.cpp.} \code{afm2gguf.py -{}-draft} writes the draft as architecture \code{afm-draft} (61\,MiB): the codes as Q4\_0 with $d=1$ (exact), $s$ as \code{token\_embd\_scale} and \code{output\_scale}, F16 projections (palette values are fp16), and an \code{output.bias} of $-\infty$ outside the draft vocabulary. The bias matters: the best draft logit is negative at about 1\% of positions, so zero rows would sometimes win. On Metal, its logits match the NumPy reference to 0.03.

Speculative decoding exposed a problem in the target graph. A verify batch [last token, 7 draft tokens] is several tokens of one sequence, which the \code{afm} graph had treated as a prompt chunk: one shared expert pick, persisted, and no input bias. Verify batches are now recognised (every token requests logits and the run does not start at position 0) and processed exactly as single decode tokens: input bias except at re-pick positions, and routing on the latest re-pick token at or before each token. Draft tokens can be rejected after they have re-picked, so the routing state now keeps two picks per sequence, each tagged with its source position. A pick from a position the batch starts at or after belongs to rolled-back tokens and is ignored. With these changes, 8-token verify batches reproduce one-token-at-a-time decoding to $2\cdot10^{-5}$ in the logits.
\paragraph{Lossless, but not faster in llama.cpp.} With greedy sampling, 7 draft tokens and no confidence cutoff (Apple's settings), \code{llama-server} with the draft returns exactly the plain answers on all 40 prompts, on Metal and on the CPU, and the plain answers are unchanged by the patch. About 11\% of drafted tokens are accepted, as the simulation predicts. Speculation is nevertheless slower in llama.cpp. Measured back to back, it was 2.1$\times$ slower on Metal and 3.5$\times$ slower on the CPU (1.8$\times$ with 3 draft tokens). A verify batch costs several single decodes here, because the 2-bit expert matmuls are compute-bound and every draft step has a fixed per-call cost. Apple's Neural Engine runs fixed-shape 8-token \code{extend} programs, so a verify step costs about as much as one token, and 0.6 extra tokens per step is a real gain there. \code{tools/eval/speculative.py} reproduces these measurements.

\paragraph{Reading the weights.} The int4 blocks resemble the 3B model's, but the header length depends on the convolution's flags: a 16-entry fp16 LUT, 32 zero bytes, the row scales, and the row biases \emph{only if} the convolution has a bias (Neural Engine register 1, bit 0x10). A 128-byte activation table precedes all of this when the convolution applies an activation (bit 0x20000). We first assumed a fixed 128-byte header, which is right only for 16-row blocks with a bias. Every bias-free block (all FFN and merger weights) was then read 4 to 12 inputs out of place, with its last inputs taken from padding. The block sizes look the same either way because each unit is padded to 64 bytes. Compiling known weights with Apple's compiler settled it: a 9216$\to$128 projection, a bias-free up projection and a SiLU-gated projection decode exactly with the flag rule and at chance level (6\%) with the fixed header. The effective bias is the stored bias times the row scale. Projection tiles are written to descending addresses, so channel order is the reversed tile order. The weights are split over two kernel sections; each block is assigned to the section where its LUT is valid. That rule is unambiguous for 1293 of 1297 blocks, and the remaining 4 follow their neighbours. Norm gains are $[\text{bias}\mid\text{scale}]$ constant tiles that the planar engine fetches; we take every gain from its fetch offset rather than from a layout formula, because the global-attention layers use a different constant layout. The compiler also folded a $0.01$ pre-norm scale into the encoder: the last residual add scales its residual operand by $0.01$ (a planar-engine operand scale, the same register that holds $1/8$ in the global layers), and $0.1$ is folded into each of the last layer's up and down projections, which are ten times smaller than every other layer's. The converter undoes this. Activations are 33-knot piecewise-linear tables: SiLU on $[-8,8]$, GELU on $[-4,4]$, with explicit linear tails.

\paragraph{Ground truth from Apple's own encoder.} Unlike the language model, the encoder's MPSGraph executable runs on the Neural Engine from our own process (about 0.8\,s per call), so Apple's encoder is a direct oracle for any input we build. A copied package does not load (``Program load failed''), so weights cannot be patched to bisect. We crafted inputs instead. When all $N$ tokens are identical, every attention layer returns $V$, so the encoder becomes a per-token function of one 1024-vector; and the merger can be inverted from the output. Before the header fix the inversion stalled at cosine 0.991 for every seed; after it, 0.99999. Our NumPy forward then matches Apple's output at cosine 0.987 on constant-token inputs and 0.95--0.97 per token on real images. The llama.cpp port matches Apple's at 0.95 and NumPy at 0.98--0.99, and its Metal and CPU paths agree to 0.9999. Every wiring choice we could vary has a sharp optimum: the alternative $V$/$O$ and gate/up/down pairings score 0.16--0.23, and in every layer each other choice of $V$ group is worse; on a real image, swapped $q/k$ scores 0.09, half-split RoPE pairs 0.50, $x$-before-$y$ 0.51 and transposed patches 0.85. Fitting per-layer branch scales gains less than 0.4 points, so the remaining percent is not a wiring error. A Core ML replica of our forward run on the Neural Engine was less faithful still (0.76), so we attribute the gap to the numerics of Apple's compiled program.

\paragraph{Through the 3B model: the RoPE layout.} Our prompt places the question, a newline and the image in the user turn, 266 tokens in total, exactly the count Apple's runtime logs for the same request. Several things the encoder program cannot tell us are chosen by Apple's host code: the pixel normalisation, the position table's interpolation, and how the 32 RoPE rotations of a head are split between the row and the column. Comparing against Apple's encoder cannot settle these, because both encoders receive whatever inputs we build. The 3B model can. With the obvious layout (row on pairs 0--15, column on 16--31) the language model received colours and scene gist but no geometry. Shuffling the 192 image tokens hardly changed anything, and asked whether a red circle is left or right, top or bottom, it answered ``Left'' and ``Top'' for all four pictures, where Apple's model answers all four correctly. The correct layout \emph{alternates}: pair $2f$ rotates by the row and pair $2f{+}1$ by the column, both at frequency $\theta_f$. With it all four spatial answers are right with margins of 5--12 logits. The mean log-probability of the key words of Apple's captions (circle, HELLO, equation, Golden, balloons, \ldots) rises from $-2.99$ to $-0.20$. The other host choices are then sharp: a negated rotation mirrors the image (``HELLO'' at $-8.2$), bilinear instead of bicubic position interpolation is worse ($-0.26$), and so is a transposed position table ($-0.21$). ImageNet normalisation is slightly better than CLIP's ($-0.20$ vs $-0.22$). With CLIP's statistics a plain white image is barely ``white'' (0.2-logit margin over gray, against 6.5 with ImageNet's), and CLIP's mean vector does not occur anywhere in the operating system's shared cache. Teacher-forced on Apple's captions of 13 images (168 tokens), our encoder gives the 3B GGUF Apple's next token 94.0\% of the time (NLL 0.29), Apple's own encoder on the same inputs 92.9\% (NLL 0.29), and no image 58.9\% (NLL 2.11). Free-running through llama.cpp with Apple's instructions, 5 of the 13 captions are identical to Apple's character for character, among them ``The word ``HELLO'' is written in black capital letters on a white background.'', and the rest are close paraphrases (``The image shows a math problem: ``2 + 3 = ?''.'' for ``\ldots a mathematical equation: 2 + 3 = ?.'').

\paragraph{In llama.cpp.} \code{afm2gguf.py -{}-vision} writes the encoder and merger as a multimodal projector (685\,MiB, F16), projector type \code{afm} in llama.cpp's \code{mtmd} library. Tokens are processed in Apple's order, with a window mask on 21 of the 24 layers. The query and key head dimensions are permuted so that llama.cpp's vision RoPE (rotating dimensions $j$ and $j{+}32$, row for $j<16$, column above) reproduces Apple's alternating interleaved pairs. Its embeddings match our NumPy forward at cosine 0.990. On an M4 an image encodes in 0.66\,s on Metal.

\paragraph{Reading it.} We read it the way we read the draft model and the image encoder: from the Neural Engine task stream rather than from symbol names. Earlier attempts (before this report) decoded every tensor but never produced text, and the reasons turned out to be the same ones the image encoder taught us. (1) The int4 header is 96 bytes (LUT, 32 zero bytes, 16 row scales; the bias flag is clear), followed by the codes and 32 bytes of zero padding; 128-byte headers had shifted every input axis by 4 positions (12 for the 128-row blocks). (2) The norm gains are not folded away: the planar engine fetches all 97 of them (four per layer and a final one) from \code{\_\_TEXT,\_\_const}, beside a $[0\mid s]$ tile that scales the hidden state before the readout and the $-40000$ vocabulary mask. (3) The embedding is a plain 8-token interleave starting at the data section; a lane ``skew'' and a 4-row shift reported earlier were both produced by a wrong base address. (4) The per-layer multiplier (9.5--12.0) applied with the key gain is not a temperature. It is the int8 scale of the key cache, and the $q\!\cdot\!k$ matmul's own fp16 scale register divides it back out: their product is $0.1250$ in all 24 layers. Values are likewise stored in int8 (scales 305 down to 10.5) and rescaled in the attention-times-$V$ matmul. (5) The two 256-wide projections are emitted in different orders: layer 0 computes $K$ first, every later layer $V$ first, as in the draft model. We assign them by dataflow: $K$ is the one whose output passes through RoPE and the head norm. Block order within a tensor follows the destination addresses (the query blocks and the up projection's are written to descending addresses), as for the encoder.

\paragraph{Results.} Apple exposes this model through no public API, so we cannot compare outputs as we do for the 3B. We test it as a language model instead. On two passages of plain English (172 and 102 tokens) its perplexity is 38.2 and 24.6, the median rank of the correct next token is 2, and it ranks it first 29\% and 39\% of the time. On random token sequences repeated twice it copies the second half 78\% of the time, the signature of trained induction heads. Each correction is necessary: with the old $K$/$V$ assignment induction is 0\% and perplexity above 100\,000; swapping $K$ and $V$ in layer 0 as well leaves perplexity above 20\,000; halving or doubling the logits raises it threefold to ninefold, so the readout is calibrated as decoded. Greedy decoding through llama.cpp:

The capital of France is $\to$ \emph{Paris.}\quad Water boils at $\to$ \emph{100\textdegree C.}\\
Once upon a time, there was a little girl named $\to$ \emph{Lily. Lily was a little girl who loved to play with her toys}\ldots\\
(chat turn) What is 12 plus 7? $\to$ \emph{12 plus 7 is 19.}\quad Write one sentence about the ocean. $\to$ \emph{The ocean is a vast, mysterious expanse of water that stretches for miles, teeming with life, diverse ecosystems, and endless horizons.}

\paragraph{In llama.cpp.} The layer is the draft model's, so \code{afm2gguf.py -{}-pico} writes it with the \code{afm-draft} architecture and no new runtime code: the embedding as Q4\_0 with unit scales (exact), the projections as F16, the full 262\,144-token vocabulary with Apple's mask as the output bias (721\,MiB). Its greedy continuations are identical to our NumPy forward's.

\paragraph{Adapters and the safety guard.} Every 300M adapter, including the default one inside the base package (\code{lora\_32/64\_constant\_data.bin}), is a flat file of fp16 $(A,B)$ pairs, $A$ as $[r,\text{in}]$ and $B$ as $[\text{out},r]$, per layer in the order attention output, $q$, $k$, $v$, \code{linear\_0}, \code{linear\_1}, FFN output. The one trap is the layer order. The pairs follow the package manifest's tensor names sorted as strings, so the layers come as 0, 10--19, 1, 20--23, 2--9. Read in numeric order, every adapter looks inert (the guard below never says ``safe''); with a plain numeric-string sort (0, 1, 10, \ldots) it half works. \code{linear\_0} is the gate (log-probability of the right first token $-0.10$ against $-0.55$ as up), the Neural Engine program scales the product by $0.5$, and every role contributes. With the order fixed, the base package's own rank-64 adapter is a trained default: it lowers the base model's perplexity from 38.2 to 30.8 and from 24.6 to 21.4 (llama.cpp, 128-token windows: 26.9 to 22.1). Twelve task adapters of rank 32 or 64 ship on our Mac, and all share its starting point: their weights correlate 0.33--0.99 with the default adapter of the same rank, where unrelated adapters would correlate near 0. The text safety guard (\code{instruct\_300m.safety}, rank 64) carries Apple's instruction: answer \code{safe}, or one line per problem of the form \code{category,mention} or \code{category,action} over 14 categories (hate\_harassment, violence\_gore, self\_harm, jailbreak, vulgarity, \ldots). Run through llama.cpp with that instruction as the system turn, it answers \code{safe} for every benign prompt and answer we tried, and labels harmful text in the requested format: \code{self\_harm,action} for a plan to self-harm, \code{jailbreak,action} for ``Ignore all previous instructions\ldots'', \code{vulgarity,action} for swearing. It separates talking about a thing from doing it: a history of the battle of Verdun gets \code{violence\_gore,mention}, a friend's past suicidal thoughts \code{self\_harm,mention}, a news report of an arrest \code{safe}. The smaller \code{mm\_guard} (rank 32, nine categories) agrees on everything except the swearing, which it calls \code{safe}; vulgarity is not one of its categories. \code{afm2gguf.py -{}-pico-adapter NAME} writes any of them as a llama.cpp LoRA with Apple's instructions in its metadata, and \code{tools/afm300m\_classify.py} runs a classifier as Apple renders it. As for the base model, there is no Apple reference to compare against: the guard's verdicts are judged by whether they follow its own instructions.

\paragraph{Images.} The 300M model has its own image encoder, \code{instruct\_300m.image\_tokenizer} (\code{ImageTokenizer}, model id \code{afm-plus-v11-300m-instruct-4bit-pal}). Its program has the 3B encoder's structure exactly: 24 layers, windows of $12\times12$ patches with full attention in layers 7, 15 and 23 (counted from the attention matmuls per layer), the same $3\times3$ merger, and a last projection to 1024 instead of 1536. Its position table differs, so it was trained separately. Two details differ from the 3B encoder. The weight palettes are sorted real-valued codebooks rather than integers, and there is no folded $0.01$ scale (the last layer's weights are in line with the others). The same decoder therefore covers both (\code{afm2gguf.py -{}-pico-vision}); the 3B projector it writes is byte-identical to before. In llama.cpp the encoder runs as the existing \code{afm} projector. The only runtime change is in the \code{afm-draft} graph, which now applies the per-dimension embedding scale to text tokens only, so that image embeddings enter unscaled. With the default adapter the 300M model describes images (``The image contains the text ``HELLO'' in a stylized font.''; ``a blue square with a white background''). The image classifiers are adapters of the same kind as the guard: \code{misc\_safety} holds Apple's instructions for violence/gore classification and for counting people (``0, 1, 2''), and \code{prepubescent\_safety} checks for children shown with adult features. On stock photos from Keynote's themes the people counter answers 0 for all four photos without people, 1 for four of five single portraits (the miss is a person whose face is hidden by a hood), 2 for two women, and 2 for three boys, where 2 is the largest answer allowed. The two safety classifiers answer \code{safe} for every benign image we tried, including synthetic red paint splatter; we did not test them on harmful images.

\paragraph{The layer-0 input: no multiplier, and a bias only for generated tokens.} Earlier drafts fitted an input multiplier $k$ and found the score flat for $k=8$--14. That scan was invalid: llama.cpp's generic embedding code already applied the GGUF's \code{embedding\_scale}, and the AFM graph applied it again, so the scan really covered $k=80$--140. Dumping llama.cpp's intermediate tensors and comparing them with an independent NumPy forward exposed a factor of exactly 10 at the layer-0 input. Scanning the true multiplier with the expert picks held fixed gives a sharp optimum at $k=1$ (mean log-loss of Apple's tokens 0.140, against 0.143 at 0.75 and 1.25 and 0.240 at 100). This matches what Apple's files say: the gather has no multiply.

With $k=1$ the body of the network and the router disagreed. The body wanted the input bias added, but the router's picks were best when the bias was negligible. We found this by computing the picks from a forward at a larger $k$, or with the bias removed; a version that changed only the layer-0 attention balance did not help (78\%). Apple's ANE program has two procedure families. The prompt procedures (\code{prompt\_opt}) add a zero constant at layer 0. The extend procedures, which compute generated tokens, add the bias vector. Applying the bias to generated tokens only is one consistent model for both parts. It reaches 95.9\% with the picks held fixed and 96.1\% in the shipped runtime, which gives the bias to single-token decode steps and not to prompt chunks. Flipping the bias's sign costs two points, so the vector is real; it simply belongs to one procedure family.

\section{What did not work}\label{sec:negative}
%======================================================================

Recorded so that nobody repeats them:
\begin{itemize}
\item Running Apple's backbone on the ANE from our own process: the kernel refuses LLM base-model requests from non-platform binaries, even with AMFI disabled.
\item Ten-plus forward variants before the gain fix: Gemma-style $1{+}g$ gains, standard residual, swapped or negated RoPE tables, embedding scales, alternative row stripes, GQA maps, within-vector gain permutations, per-row scale permutations---all 0\% top-1, because the defect was elsewhere.
\item LoRA as the missing piece: the Foundation Models API's generic adapter for v11.2 is untrained (B RMS $3\cdot10^{-5}$), so the base model is already what the public API runs. Its ``signature'' (the SHA-256 of the empty string) proves nothing, because the trained feature adapters carry the same one (Section~\ref{sec:adapters}).
\item Apple's \code{MODLM current context $N$ asked to run $K$ tokens} log as an oracle for draft acceptance: it interleaves the guard model, the target and the draft (and several generations) with no stream id, and the draft's catch-up calls are only ever 1 or 3 tokens, so per-step acceptance cannot be read off it.
\item Patching Apple's image encoder to bisect it: a copied MPSGraph package does not load on the Neural Engine. A Core ML replica of our encoder on the Neural Engine was less faithful (0.76) than NumPy (0.987).
\item Before the alternating RoPE layout was found, we tried to restore spatial understanding with RoPE position rescaling (the RoPE table has 481 rows; $\times10$ or fit-to-480 positions), window-relative positions, other window, group, patch and output orders, cropped position tables, collapsed LLM positions for the image tokens, bidirectional attention over them, rescaled embeddings, no int8 K/V emulation and image-before-question prompts. None helped. Each of them leaves the axis layout unchanged, so they could not.
\item Weight statistics such as ``alignment ratios'' and residual-collapse measures: uncalibrated, and on a healthy model indistinguishable from AFM.
\item The earlier attempts on the 300M model (from symbol names, compiled probes and permutation searches) recovered the tile element order exactly but never produced text. Their conclusions---no norm gains ship, the embedding has a lane skew and a 4-row shift, the residual-writing projections hide an unreadable layout, some layers' FFNs ``hurt''---were all consequences of the 128-byte header, the wrong embedding base and the positional $K$/$V$ assignment (Section~\ref{sec:pico}).
\item Reading the 300M adapters' layers in numeric order. Every adapter then looks inert, and the base package's default adapter even looks slightly harmful; we briefly took it for a placeholder. The files follow the manifest's string-sorted tensor names (Section~\ref{sec:pico}).
\item Pooled expert routing rules (mean of inputs, of logits, of probabilities; prompt or user turn; prefix mean, vote counts): all below per-token routing, and all wrong---Apple routes from a single token (Section~\ref{sec:runtime}). They had looked plausible only because our template was wrong.
\item Routing from the layer-12 FFN input instead of its attention input: 89.4\% teacher-forced, and three times too many experts changed per re-pick (109 versus Apple's 36).
\item Reading Apple's between-prompt expert changes from the cache log: those counts (361--556 of 1012) include cache eviction while the service is idle and do not measure pick differences; only re-picks within one generation do.
\end{itemize}

%======================================================================
\section{Toward 100\%}\label{sec:open}
%======================================================================

The prompt template, the expert schedule, the layer-0 input and the activation function are now Apple's own. 37 of 1127 answer tokens still differ. Apple's token is almost always our second or third choice. Earlier drafts called the remaining gap a numerical noise floor; the layer-0 bug shows that this was premature. What we measured directly:
\begin{enumerate}
\item \textbf{The ANE's matrix multiplies are accurate.} We ran our own CoreML programs on the Neural Engine, confirming the device with Core ML's compute plan. Sums accumulate at high precision and only the fp16 output is rounded (relative error $2.8\times10^{-4}$, the same as fp32 accumulation with an fp16 result). The low-precision accumulation one first sees comes from Core ML's fp16 CPU path, not the ANE.
\item \textbf{Its SiLU is a 33-knot piecewise-linear table} (knots every 0.5 on $[-8,8]$, fitted values, for example $0.2964$ at $x=0.5$ where SiLU is 0.3112). The same 128-byte table appears 2113 times in AFM's ANE program, once per FFN task, and it is the program's only activation table. We tabulated it for all 65\,536 fp16 inputs. It is exactly linear interpolation between the knots, with a left tail clamped to zero below $-10.2$ and $x-0.0039$ above 8, rounded to fp16. In the v1.0 setup emulating it was neutral (10 fixed, 8 broken) because the layer-0 error dominated. On the corrected model it fixes 14 and breaks 5 tokens (96.10\% $\to$ 96.72\%), so it is now the default. Its softmax, exp and rsqrt are also approximate (0.3--0.4\% relative error).
\item \textbf{Apple's speculative decoding is exact.} Every FM-API adapter sets \code{draft\_soft\_match\_tolerance} to 0 and turns rejection sampling off, so the draft model never changes a greedy token. The FM-API adapter is the declared-empty adapter (signature = SHA-256 of the empty string), and there is no repetition penalty.
\item \textbf{The router is robust to arithmetic.} Computing it with fp16 accumulation moves 0.01 of 23 experts per layer-pick, and random noise strong enough to swap a third of an expert per layer changes 2\% of predictions without moving the agreement.
\end{enumerate}
Every weight, gain, bias, the router, the tokenizer, the template and the routing rule come from Apple's files and code; nothing was trained or fine-tuned.

\paragraph{Path noise.} On the final model, the CPU and Metal backends (identical mathematics) disagree on 0.71\% of answer tokens (8/1127), and their agreement with Apple is identical (96.72\%). The remaining 37 misses are near-ties: Apple's token is our second choice in 84\% and always in our top three, and the median logit gap is 0.40. Rounding every matmul output to fp16, as the ANE stores it, gives 96.89\% (within noise). In v1.0, mathematically identical variants disagreed on 0.1--2.4\% of next-token choices: fp16-rounded activations against fp32, llama.cpp's RoPE kernel against an elementwise one, or one batch against a prompt batch followed by single steps. The 2-bit weights and the int8 KV cache amplify rounding, so a percent or so of residual disagreement is expected even from an exact model.

\paragraph{A larger test.} The 40-prompt set moves by about $\pm0.4\%$ from noise alone, so we added 190 prompts (6572 answer tokens in all) and re-ran every candidate (Table~\ref{tab:ext}). The Neural Engine SiLU is worth a full point. Every other ANE detail we could emulate is neutral: fp16 matmul outputs, int8 KV on or off, keys quantised before their gain, and fp16 RoPE tables. Truncating instead of rounding the int8 cache costs a point, so Apple rounds to nearest. Of the remaining 316 misses, 2.9\% of tokens are missed under any routing and 1.9\% only under Apple's schedule. The latter is consistent with our prompt-level pick differing from Apple's by a boundary expert or two: the 23rd and 24th router logits are a median 0.003 apart, about the size of a rounding difference in the layer-12 state. Apple's log also confirms the re-pick timing. Around a boundary the runtime steps one token at a time, and the pick at position 96 uses token 96 itself. Apple's fp16 logits never tie at the top, and its softmax errors (about 0.2\% in the denominator) cancel in the post-attention RMS norm.

\paragraph{Running the dense layers on the Neural Engine.} As a direct test of the arithmetic, we rebuilt layers 0--11 as a Core ML program, which placed every operation on the ANE: int8 KV round and clip, the ANE's own SiLU and softmax. We fed its layer-12 state to llama.cpp for routing and the remaining 44 layers. The state differs from our emulation by about 15\% (relative norm) after 12 layers; in isolation each layer's FFN agrees with our SiLU-table model to fp16 rounding (0.5\%), and int8 steps in the very coarse layer-0 values amplify the differences. Agreement with Apple stays the same: 94.92\% against 95.19\%, but 224 of 6572 tokens flip (103 fixed, 121 broken). The control, the same program in fp32 on the CPU with exact SiLU, gives 94.42\%. So two plausible versions of the hardware arithmetic disagree on about 3.4\% of tokens without either being closer to Apple, which is the size of the remaining gap. Core ML compiles our graph differently from Apple's hand-built ANE program, so even the real hardware does not reproduce Apple's rounding. Closing the last points would need that program's exact arithmetic.

\paragraph{Apple's own expert decisions.} Apple's runtime logs every pick per layer (``layer $N$ experts: \dots''). The expert list is marked \emph{sensitive}, so it stays redacted even with a logging profile that enables private data for the inference service. That profile does reveal the subsystem's ordinary private values. The cache statistics are public, though. At each pick the runtime logs \code{reordered}, \code{replaced} and \code{loaded}, and within one answer the cache holds exactly the current pick, so \code{replaced} at a re-pick counts the experts that changed. Over the 135 re-picks in the 230-prompt set, our router's predicted churn tracks Apple's with $r=0.934$ and a mean miss of 4.6 of about 40 changed experts. That bounds our picks to within a few of Apple's 1012 per pick. Moving the re-pick to a neighbouring token makes the match clearly worse (5.3--5.4), which pins the schedule. Every arithmetic variant scores the same within noise: 4.50 for the ANE-computed layer-12 state, 4.60 for the default, 4.60 for fp16 matmul outputs, 4.65 for fp32 with exact SiLU, 4.67 for exact SiLU, and 4.45 without the input bias at re-pick tokens. Apple's re-picks change slightly fewer experts than ours (by 1.6 on average). A small preference for already-loaded experts fits the counts only marginally better (4.60 to 4.40) and costs words (95.15\%), so we reject it. Apple's code runs a dense-only function at each re-pick token, the same procedure family as the prompt, which adds no layer-0 bias. Dropping the bias at those tokens is v1.3's only change: 95.19\% $\to$ 95.27\% (12 fixed, 7 broken). Between prompts the counts do not track the previous prompt's pick (Apple 501 on average, our prediction 111), so the cache is not simply carried over between requests.

At 89 of the 93 our choice was an ordinary text token, so Apple's output masking is not involved. Table~\ref{tab:night} lists the numerical experiments, run on the v1.0 configuration.
