\title[Apple's On-Device Foundation Model, Rebuilt]{Apple's On-Device Foundation Model, Rebuilt:\\
A From-Weights Reconstruction of \code{afmplus-v11.2-ifp}\\ and a Portable llama.cpp Runtime}
\author{Yu Yao-Hsing}
\email{euler.yu@gmail.com}
\date{November 14, 2026}

\begin{abstract}
Apple's on-device foundation models are distributed as proprietary assets compiled for the Neural Engine, which makes their structure and inference behaviour difficult to study outside Apple's runtime. We reconstruct the language model that Apple Intelligence installs on macOS~27, \code{afmplus-v11.2-ifp}, from its shipped assets, and implement a portable inference backend for it in llama.cpp. The recovered model has 56 transformer layers and 20.30 billion stored parameters. It combines dense layers, sparse feed-forward experts selected by a router (Instruction-Following Pruning), and key/value reuse across its last 21 layers. We decode the quantised weights and the tokenizer, identify a non-standard residual formulation in which both residual additions carry normalised values, and recover the prompt format and the expert-selection schedule from Apple's inference frameworks. No parameter is trained or fitted.

We evaluate against Apple's own model, queried through the public Foundation Models API at temperature zero. Under teacher forcing, the reconstruction's greedy next-token prediction matches Apple's at 95.66\% of positions on a held-out set of 100 prompts (2{,}900 reference tokens) that played no part in development, and at 95.19\% on the 230 prompts (6{,}572 tokens) used during development. This is a measure of token-level agreement, not of full-response identity: 51 of the 100 held-out answers are reproduced character for character. Exact numerical equivalence with Apple's compiled Neural Engine program is not achieved; the remaining disagreements are concentrated at near-ties between the two most likely tokens.

We also decode the companion components---the feature adapters, the speculative-decoding draft model, the image encoder, and the 300M model with its safety guard---and validate each to the extent that a reference exists. The released converter and runtime patch rebuild the models from assets already present on the user's Mac; no Apple weights are redistributed.
\end{abstract}

\section{Introduction}\label{sec:intro}
%======================================================================

Modern on-device language models are often available to users only through a platform API, even when their parameter data reside on the user's own computer. Reproducing such a model requires more than extracting tensors: the execution graph, the compressed storage layout, the tokenizer, the prompt convention and the runtime's policies each affect its output, and for a model compiled for a proprietary accelerator none of them is documented. Apple's on-device foundation model is a case in point. Its weights ship inside a compiled Apple Neural Engine (ANE) program whose format is undocumented; its feed-forward layers are sparse, with the active subset chosen at run time by code that is not part of the model files; and the kernel refuses to run the program on behalf of third-party processes (Appendix~\ref{sec:negative}). Published descriptions of Apple's models~\cite{gunter2024afm,hou2025ifp} give the design principles but not the shipped model's dimensions, storage format or scheduling rules.

This study asks how much of one locally installed Apple foundation model can be reconstructed from its model assets and from observable platform behaviour, without retraining the model and without redistributing its parameters.

\paragraph{What ``reconstruction'' means here.} We recover the model's stored tensors, its principal computation graph and the runtime policies that can be observed from outside (the prompt template and the expert-selection schedule), and we implement a portable approximation of its inference behaviour. We do not claim numerically identical execution: the exact arithmetic of Apple's compiled Neural Engine program is not reproduced, and Section~\ref{sec:open} quantifies what that leaves open.

\paragraph{Contributions.}
\begin{enumerate}
\item \textbf{A structural reconstruction} of the installed \code{afmplus-v11.2-ifp} language model and its weight encodings: 56 layers, a post-normalised residual with four learned gains per layer, grouped-query attention with an int8 key/value cache shared by the last 21 layers, and a sparse feed-forward network with 23 always-on and 23 routed experts per layer (Sections~\ref{sec:arch}--\ref{sec:bug}).
\item \textbf{A converter and a llama.cpp implementation} of the recovered architecture. The 2-bit weights map onto an existing GGUF quantisation type without loss, and the runtime runs on macOS, Linux and Windows (Sections~\ref{sec:llama} and~\ref{sec:converter}).
\item \textbf{A reconstruction of prompt rendering and expert routing} from Apple's inference frameworks and runtime logs (Section~\ref{sec:runtime}).
\item \textbf{An evaluation against Apple's own model}, with ablations that isolate the implementation details that matter and a held-out test that was not used during development (Sections~\ref{sec:method} and~\ref{sec:fidelity}).
\item \textbf{An analysis of the companion components}---feature adapters, draft model, image encoder, 300M model and safety guard (Sections~\ref{sec:adapters}--\ref{sec:pico})---and of the remaining numerical discrepancy (Section~\ref{sec:open}).
\end{enumerate}

\paragraph{Sources of evidence.} The claims in this paper rest on evidence of four kinds, and we try to keep them apart. \emph{Asset bytes} are directly observed: file contents, tensor values, constants. \emph{Program interpretation} is inference from compiled artefacts---the Neural Engine task stream, register values, disassembled framework code---about what the model computes. \emph{Controlled comparison} checks an interpretation against a reference we can run: Apple's model through the public API, Apple's own compiler applied to known weights, Apple's image encoder executed directly, or values in Apple's runtime log. A \emph{hypothesis} is consistent with the evidence but has not been tested directly. Table~\ref{tab:ledger} classifies the principal claims. We use ``observed'' for asset bytes and log values, ``validated'' for controlled comparisons, and ``indicates'' or ``is consistent with'' for indirect evidence.

\section{Identification of the model}\label{sec:which}
%======================================================================

Apple's third-generation foundation models (announced June 2026) comprise two on-device language models and several Private Cloud Compute models (Table~\ref{tab:lineup}). The macOS~27 SDK exposes the on-device model as \code{SystemLanguageModel} and the server models through \code{PrivateCloudComputeLanguageModel}. The assets on the device contain exactly one foundation language backbone, \code{afmplus-v11.2-ifp}; the server models are present only as adapter metadata (\code{afmplus-v8.0-150b}, \code{afmplus-v9.0-3b-pcc}).

\noindent Apple does not publish a mapping from asset identifiers to product names, so the name is an identification, not a disclosed fact. Based on three observations we identify the local asset with the on-device tier described as \emph{AFM~3 Core Advanced}: the converted model holds 20.30\,B parameters; its feed-forward network is Instruction-Following-Pruned; and the Foundation Models API ships three compute budgets (\code{fm\_api\_generic\_1b/2b/3b}) that select 5, 14 or 23 routed experts, which correspond to about 1.2, 2.1 and 3.0\,B parameters used per token (Table~\ref{tab:params}). It is not a ``Pro'' model: by the same public descriptions the Pro model runs only on Apple's servers, and no such asset is present on the device. In the rest of the paper we refer to the model by its asset version, \code{afmplus-v11.2-ifp}, or by Apple's size-class name ``3B''.

\subsection{The layer: a post-normalised ``x/y'' residual}

In a standard pre-norm transformer the residual stream $h$ is never normalised: each sublayer reads a normalised copy of $h$ and adds its output to the unnormalised $h$. This model differs in two ways. The stream itself is renormalised before each sublayer, and each sublayer's output is normalised again before it is added. Both operands of both residual additions are therefore normalised vectors scaled by a learned gain.

Notation: $h_{L-1}$ is the output of layer $L-1$; $x_L$ is the normalised input of layer $L$'s attention and $y_L$ the normalised input of its feed-forward network; $h'_L$ is the intermediate sum after attention. Each layer carries four learned RMSNorm gains $g_0,\dots,g_3\in\mathbb{R}^{1536}$, where $g_0$ scales the attention output, $g_1$ produces $y$, $g_2$ scales the feed-forward output, and $g_3$ produces the next layer's $x$:
\begin{align*}
x_L &= \mathrm{rms}(h_{L-1})\odot g_3^{L-1}\qquad(\text{layer 0: } x_0 = k\,e_t + b,\ \text{no norm})\\
h'_L &= x_L + \mathrm{rms}\big(\mathrm{Attn}_L(x_L)\big)\odot g_0^{L}\\
y_L &= \mathrm{rms}(h'_L)\odot g_1^{L}\\
h_L &= y_L + \mathrm{rms}\big(\mathrm{FFN}_L(y_L)\big)\odot g_2^{L}
\end{align*}
with $\mathrm{rms}(v)=v/\sqrt{\mathrm{mean}(v^2)+\varepsilon}$ (RMSNorm~\cite{zhang2019rmsnorm}), gains used literally (no $1+g$), and a final output $\mathrm{rms}(\mathrm{rms}(h_{55})\odot g_3^{55})\odot g_\mathrm{out}$ multiplied by the tied embedding. Read as one step: layer $L$ normalises the previous output into $x_L$; attention reads $x_L$, and its normalised output is added to $x_L$ itself, not to $h_{L-1}$; the sum is normalised into $y_L$; the feed-forward network reads $y_L$, and its normalised output is added to $y_L$. We call this the ``x/y'' residual after the two normalised streams.

The wiring is an interpretation of the ANE program's memory-transfer (DMA) pattern: the normalised attention input is written to scratch memory and read back by the attention residual add, and the feed-forward residual add reads the normalised feed-forward input. It is validated against Apple's outputs: with a standard residual and otherwise identical weights the model scores 0\% top-1.

\subsection{The Instruction-Following-Pruned feed-forward network}

Sparse layers add two SwiGLU~\cite{shazeer2020glu} blocks without any gating weights:
\[
\mathrm{FFN}(y)=\underbrace{\sum_{e=0}^{22}\mathrm{SwiGLU}_e(y)}_{\text{always on}}\;+\;\underbrace{\sum_{e\in\mathcal{S}(y)}\mathrm{SwiGLU}_e(y)}_{|\mathcal{S}|=23\text{ routed}},\qquad
\mathrm{SwiGLU}_e(y)=W^{\mathrm{down}}_e\big(\mathrm{SiLU}(W^{\mathrm{gate}}_e y)\odot W^{\mathrm{up}}_e y\big),
\]
each expert being $256$ wide. The ANE program runs the always-on experts from static kernels and the routed experts from a mutable kernel patched at runtime from \code{ifp\_rasterized\_weights.bin}. Both halves matter: the always-on experts alone reach 62.9\% top-1, the routed experts alone 1.4\%, both together 87.5\% (measured with the single-turn template).

\paragraph{Expert indices.} The expert index space of a sparse layer runs from 0 to 379. Experts 0--22 are always on. The router's mask excludes indices 0--31, so the 348 experts 32--379 are the eligible routed ones, of which the 23 with the largest router logits are active. Indices 23--31 are neither always on nor routable.

\paragraph{When experts are chosen.} Apple's runtime does not route per token. It runs the dense layers over the whole prompt, takes the layer-12 input of the \emph{last} prompt token, runs the router once, and uses that expert set for every prompt token and for generation; it re-picks from the current token only at absolute positions that are multiples of 32. Section~\ref{sec:runtime} shows how this was read out of Apple's inference framework.

\caption{The 2-bit weight unit. A projection is split across the 16 ANE units bank-cyclically; a chunk with more banks holds the lower bank slots. The value of a weight is $w = s_m\,(c-1.5)$ with $c\in\{0,1,2,3\}$ and $s_m$ the fp16 row scale. Experts in \code{ifp\_rasterized\_weights.bin} use the same codes with a simpler order: code $p\mapsto$ (row $16\lfloor p/(16\,\mathrm{in})\rfloor + p\bmod 16$, input $\lfloor p/16\rfloor \bmod \mathrm{in}$).}\label{fig:tile}
\end{figure}

\paragraph{Exact GGUF encoding.} llama.cpp's Q2\_K stores, per 256 weights, sixteen 4-bit sub-block scales $\mathit{sc}$ and mins $m$, a super-scale $d$ and super-min $d_{\min}$, and evaluates $w = d\,\mathit{sc}\,c - d_{\min}\,m$. Choosing $\mathit{sc}=2$, $m=3$ and $d=d_{\min}=s/2$ gives
\[
w = \tfrac{s}{2}\cdot2c-\tfrac{s}{2}\cdot3 = s\,(c-1.5),
\]
where $c\in\{0,1,2,3\}$ is the 2-bit code and $s$ the fp16 row scale. Halving an fp16 number is exact (barring underflow, which does not occur in these scales), so $d$ and $d_{\min}$ are representable. The int4 embedding ($w=s_t\,q$, $q\in[-7,7]$, per-token fp16 scale $s_t$) maps exactly onto Q4\_0 with $d=s_t$ and nibble $q+8$. \paragraph{What ``lossless'' means here.} The claim concerns decoded real values: the number a GGUF reader obtains for a weight equals the number Apple's format encodes, $s\,(c-1.5)$ or $s_t\,q$, exactly. It rests on the algebra above, and on a check in which 55 million weights were dequantised with gguf-py and compared with the values decoded directly from Apple's files, with a maximum absolute difference of 0. That check was a sample, not an exhaustive comparison of all 20.3 billion weights. A separate statement, that the converter's output is byte-identical to the file used for our measurements (Section~\ref{sec:converter}), concerns reproducibility of the conversion and is a different test. Neither says anything about arithmetic at inference time, where llama.cpp and the Neural Engine differ (Section~\ref{sec:open}).

\paragraph{Layout facts and how they were ground-truthed.} We compiled known weights through Apple's own ANE compiler (\code{mil\_to\_hwx -a h16}) and decoded the result: the output axis is the bank-cyclic stripe above, the input axis is natural, the codebook and row scales are as in Figure~\ref{fig:tile}, and constants (gains, biases) are stored in natural order. A calibrated copy-circuit probe (Section~\ref{sec:validate}) is consistent with the stripe, the head order and the V/O pairing: every alternative layout scores at chance.

\begin{finding}
An initial parse located the table by statistical signatures and accepted a start two bytes early. Every RMSNorm therefore multiplied channel $r$ by the gain of channel $r{-}1$. Because $g_0$ and $g_2$ are zero-centred, this flipped the sign of about a third of every residual write at every layer, and the assembled model predicted nothing (0\% top-1, no induction).
\end{finding}

\paragraph{How it was found.} No tensor was defective in isolation: each was correctly laid out and correctly paired. The decisive step was to calibrate probes on a healthy Apple model and then to compare \emph{reader--reader} with \emph{reader--writer} relations. In AFM, query--key and gate--up relations were as healthy as in CodeLM, but value--output (copy heads) and up--down (FFN neuron coupling) relations were weak. In a trained network, the sign of the coupling between up-row $i$ and down-column $i$ agrees with the sign of the gain that scales the write. In AFM the \emph{number} of negatively coupled channels equalled the number of negative entries of $g_2$ in every layer---while their \emph{positions} disagreed (Figure~\ref{fig:offbyone}, left). Matching each channel's 11-layer sign signature against the table gave a constant offset of one element. Read aligned, the agreement rises to 98--99.9\% (right) and the model works: 66\% top-1 against Apple's outputs immediately, rising to 87.5\% with the llama.cpp implementation and exact tokenization.

\section{Validation instruments and their calibration}\label{sec:validate}
%======================================================================

The gain-table defect was found with diagnostic probes whose readings on a known-good model were established first. This section describes the reference, the calibration model and the probes; Section~\ref{sec:method} gives the evaluation protocol proper.

\paragraph{The reference.} \code{afm -t 0} (a small Swift wrapper around the Foundation Models API) produces Apple's greedy answers. At temperature zero the token Apple emits at each answer position is its most likely one, so teacher-forced top-1 agreement compares our prediction with an absolute target. The API exposes no probabilities.

\paragraph{The copy probes.} Two probes are used below, in the sense of the circuits analysis of~\cite{elhage2021framework}. The \emph{OV copy probe} asks whether an attention head, when it attends to a token, writes that token back to the output. For a head with value and output projections $W_V$, $W_O$ and a token $t$ with embedding $e_t$, it computes the readout $E\,W_OW_V\,e_t$ over the vocabulary and records the rank of $t$ itself (0 is best). A head's score is the median rank over a fixed sample of tokens, and a layer's score is that of its best head. A head whose output is unrelated to token identity scores near half the vocabulary size (131{,}072 for AFM), which we mark as chance. The \emph{same-token QK probe} is the analogous rank for attention scores: among keys built from sampled tokens, the rank of the key that belongs to the query's own token.

\paragraph{A healthy reference: CodeLM v3.} Xcode's on-device code model ships as a GPU MPSGraph package. Its MLIR (via \code{-getIR}) is a complete, readable tamm transformer---pre-norm, standard residual, RoPE then QK-norm, SwiGLU, KV reuse from layer 34, int4 weights with group-32 scales---with the same backbone shape as Apple's other 3B-class models (56 layers, 35 KV-owning, 2048 wide, 16/2 heads). We ran it on the GPU from our own process through \code{MPSGraphExecutable} (100\% induction accuracy) and reproduced its logits in NumPy exactly (correlation 1.00000, 100\% argmax agreement). Its tokenizer and embeddings are unrelated to v7-3b's, so it cannot donate weights, but it calibrates the probes.

\paragraph{What the calibration showed.}
\begin{itemize}
\item \emph{Zero-centred literal gains are normal} in tamm (CodeLM's pre-attention gain: mean $+0.003$, 46\% negative).
\item \emph{The embedding--weight ``alignment ratio'' used earlier in this work is not diagnostic}: a healthy model scores the same (1.0--1.4).
\item \emph{The OV copy probe is diagnostic}: CodeLM has several heads that map a token to itself at rank 0--16, even after naive 2-bit rounding; decoded AFM had none below rank 1000 (Figure~\ref{fig:copy}). Every alternative V/O layout scored at chance, which argued against a layout error and directed attention to the gains.
\item \emph{The same-token QK probe} found AFM's query--key circuits healthy (rank-0 heads) and confirmed the head pairing $h\mapsto\lfloor h/2\rfloor$.
\end{itemize}

Healthy CodeLM has rank-0 heads; AFM's raw $W_OW_V$ peaks at weak copying because in AFM the write passes through the signed gain $g_0$, whose positions were scrambled by the table shift.}\label{fig:copy}

\paragraph{Apple's int8 calibration as a ground truth.} The ANE program stores per-layer scales for its int8 K/V cache. With the corrected gains, the reconstruction's values stay inside Apple's ranges, and its keys stay inside up to the 99.9th percentile; only the most extreme 0.1\% of keys would clip (Figure~\ref{fig:kv}). \section{Apple's runtime: the prompt template and the expert schedule}\label{sec:runtime}
%======================================================================

Two things the model files do not contain decide what the model sees and which experts it uses: the prompt template (the metadata only names it, \code{afm\_cider\_v2}) and the rule for choosing experts. Both live in code, in two private frameworks of the dyld shared cache: \code{TokenGenerationCore} renders and tokenizes prompts, \code{TokenGenerationInference} drives the model. \code{dyld\_info -disassemble} prints both with Swift symbol names. One detail matters for reading them: Swift stores string literals of up to 15 bytes inside the instruction stream (\code{mov}/\code{movk} immediates), so \code{<start\_of\_turn>} and the other markers do not appear in a strings dump.

\subsection{The prompt template}
\code{PromptPreprocessingTemplateAfmCiderV2Convention} takes its special-token table from the older Cider~v1 convention and overrides only audio and reasoning entries. Decoding the immediates gives turn start \code{<start\_of\_turn>}, turn end \code{<end\_of\_turn>}, and roles \code{system\textbackslash n}, \code{developer\textbackslash n}, \code{user\textbackslash n}, \code{model\textbackslash n}; the ``thought budget: none'' and ``developer static instructions'' entries are empty. Its \code{cacheableSystemPrefix} concatenates
turnStart, the system role with Apple's default instructions, the thought budget, turnEnd, a newline, then turnStart and the developer role. A FoundationModels conversation therefore renders as
\begin{center}\small
\code{<bos><start\_of\_turn>system\textbackslash n}\emph{default}\code{<end\_of\_turn>\textbackslash n}\\
\code{<start\_of\_turn>developer\textbackslash n}\emph{instructions}\code{\textbackslash n<end\_of\_turn>\textbackslash n}\\
\code{<start\_of\_turn>user\textbackslash n}\emph{prompt}\code{<end\_of\_turn>\textbackslash n<start\_of\_turn>model\textbackslash n}
\end{center}
where \emph{default} is the \code{systemInstructions.default} text of the adapter metadata (``A conversation between a user and a helpful assistant. You are a foundation model developed by Apple. \ldots'') and the developer turn holds the app's instructions. The public API confirms the rendering: \code{SystemLanguageModel.tokenCount(for:)} accepts transcript entries and returns the length of the rendered prompt, which equals the length the inference service logs (``asked to run 71 tokens'') for the same conversation. Table~\ref{tab:tc} compares it with our rendering. A template that folds everything into one system turn and omits the instructions passed by the reference client scores markedly lower; with the exact template, teacher-forced agreement rose from 87.5\% to 90.5\% and the first answer token from 30 to 38 of 40.

\subsection{The expert schedule}
The inference log of a single request already shows the shape of the algorithm: a ``prompt expert compute function'' (\code{lora\_48\_ifp3\_r48\_prompt\_opt\_dense\_only\_256\_64}, the dense layers only) runs over all prompt tokens, then ``Picking IFP experts at position=70 isPromptPick=true'' for a 71-token prompt, then the sparse layers run over the \emph{whole} prompt again with the picked experts. The dense-only function returns a \code{1536}$\times$\code{64} fp16 tensor per 64-token chunk, one column per token. In \code{TokenGenerationInference}, \code{computePromptExpertState} builds the router input with \code{IFPDenseLayerOutput.makeExpertsTensor(tokenIndex:)}, whose loop copies the 1536 values of a single column into a $1536\times1$ tensor---no mean, no accumulation. The router (\code{project\_experts}, the network of Figure~\ref{fig:ifp}) then yields the top-23 experts per sparse layer. During generation, \code{repickExpertsAtBoundary} calls the same picker, and \code{IFPExpertPicker} rejects any intermediate pick whose position is not a multiple of \code{expert\_selection\_frequency} (an \code{sdiv}/\code{msub} remainder test against 32). With prompt length $P$, token $t$ therefore uses the experts chosen from $x_{12}$ at
\[
s(t)=\max\!\big(P-1,\;32\lfloor t/32\rfloor\big),
\]
so every prompt token uses the last prompt token's choice. Positions are zero-based and absolute: they count every token of the rendered prompt, including \code{<bos>} and the template's markers, and continue through the answer. For the 71-token prompt of the log above, the prompt occupies positions 0--70 and all of it uses the pick made from position 70. The generated tokens at positions 71--95 keep that pick. The token at position 96 is the first multiple of 32 after the prompt: the router is run on that token's own layer-12 input and its pick applies to positions 96--127; the next re-pick is at position 128.

Averaging over the prompt instead scores much lower (79.3\% teacher-forced), and the single-token rule outperforms per-token routing (Section~\ref{sec:fidelity}).

\paragraph{An outside check of the router.} Each pick also logs \code{CacheExpertExpertCache: \ldots\ replaced=}$n$, the number of (layer, expert) choices that changed. We ran six long generations on Apple's model, collected its 47 re-picks, replayed the same token sequences through our model and counted how many of our choices change at the same positions. With the single-token rule on the layer-12 attention input the two series agree closely (Figure~\ref{fig:repick}: mean 26.7 versus 27.1 experts, correlation 0.84); prefix means correlate at 0.21--0.53 and the FFN-input variant changes three times too many. This supports the router input, the router network and the rule independently of any answer text. It is an indirect test: the log reports how many (layer, expert) choices changed, not which, so agreement in the counts does not establish that the selected experts are identical. The correlation is a Pearson coefficient over the 47 re-picks; Section~\ref{sec:open} repeats the comparison on 135 re-picks.

\section{The llama.cpp implementation}\label{sec:llama}
%======================================================================

The patch to llama.cpp~\cite{llamacpp} adds one architecture, \code{afm}, in \code{src/models/afm.cpp}, together with the supporting changes listed below.
\begin{itemize}
\item \textbf{Graph.} Layer 0 takes the dequantised embedding row as is (no multiplier) and, for generated tokens other than re-pick tokens, adds the input bias (Section~\ref{sec:fidelity}); each later layer normalises the previous output with $g_3$; queries and keys use \code{rms\_norm}, NEOX RoPE, then a gain multiply; the residuals follow Figure~\ref{fig:layer}. Sparse layers run the always-on experts as a ``shared expert'' SwiGLU of width 5888 and the routed experts with \code{mul\_mat\_id}, summed by one row reduction with no weights. The router network lives on layer 12 and its logits are sliced per layer. The output applies the double norm and the tied embedding.
\item \textbf{KV reuse.} Layers 35--55 call attention with null K/V, and the cache maps them to layer 34. This needed a two-line fix in the non-sliding-window attention path, which assumed K/V were always present.
\item \textbf{Metal kernels.} Metal's batched expert matmul is instantiated for specific experts-per-token counts; we added 14 and 23 (ifp2, ifp3). CUDA uses a generic path for such counts, and Vulkan supports Q2\_K expert matmuls, so no change is needed there.
\item \textbf{Apple's expert schedule.} The router's logits for each sequence persist in a small device buffer (64 sequence slots) owned by the model. A custom graph input computes, per micro-batch on the host, which logits every token uses: a run of several tokens of one sequence is a prompt chunk and takes its last token's logits, which are stored; a single decode token re-picks only when its position is a multiple of 32 and otherwise reads the stored choice. Because the indices are data rather than graph structure, llama.cpp's graph reuse and multi-sequence batching stay correct. Speculative verify batches are handled as single decode tokens, with two position-tagged picks per sequence so that rejected draft tokens leave no trace (Section~\ref{sec:draft}). \code{AFM\_ROUTE\_TOKEN=1} restores per-token routing.
\item \textbf{Embedding scale.} llama.cpp's generic \code{build\_inp\_embd()} multiplies by the GGUF's \code{embedding\_scale} (a Granite feature), so an architecture graph that applies the scale itself applies it twice. Apple uses no multiplier (Section~\ref{sec:fidelity}); the \code{afm} loader therefore ignores the key, which also keeps GGUFs written by earlier versions of the converter correct.
\item \textbf{The Neural Engine SiLU.} The activation is the ANE's piecewise-linear table, built from standard ggml operations: a clamp, a magic-constant floor, two 38-entry \code{get\_rows} tables and a relu for the right tail, then rounded to fp16. It costs about 45\% of prompt speed and 20\% of generation speed on Metal; \code{AFM\_EXACT\_SILU=1} switches back to the exact function.
\item \textbf{Router on the CPU.} The router's top-23 margins (median 0.003) are close to the error of Metal's tiled matmul ($8\cdot10^{-5}$ against $2\cdot10^{-7}$ on the CPU; 0.002 expert swaps per layer-pick). Its weights are therefore placed on the CPU, which makes picks identical across backends. The routing state and SiLU tables stay on the layer's device. Agreement is unchanged within noise.
\item \textbf{int8 KV emulation.} The GGUF carries Apple's per-layer K/V scales; keys and values are rounded and saturated to int8 before caching. Rounding uses the fp32 magic constant $1.5\cdot2^{23}$, because \code{ggml\_round} misbehaved on Metal.
\end{itemize}

\section{Evaluation methodology}\label{sec:method}
%======================================================================

\paragraph{Reference.} The reference is Apple's own model, queried through the public Foundation Models API with greedy sampling (temperature 0) and the instructions ``You are a helpful, concise assistant.''. Each prompt is sent in a new session by a small command-line client (\code{tools/afm.swift}; \code{tools/eval/collect\_oracle.sh}). The API returns text only: no token ids, probabilities or internal state. The answers are deterministic; repeated requests return the same text. The development references were collected on macOS~27.0 build 26A5378n. The held-out references were collected on 14 November 2026 under build 26A428; five development prompts re-collected on that day returned byte-identical answers, so we treat the model as unchanged.

\paragraph{Prompt sets.} Three sets are used (Table~\ref{tab:promptsets}); all three are published with the code. All prompts are short English requests of the kind an assistant receives: factual questions, explanations, lists, short writing tasks. The \emph{first development set} (40 prompts) was written at the start of the project, and every debugging step described in this paper used it. The \emph{development extension} (190 prompts) was added on 8 November 2026 because the first set moves by about $\pm0.4\%$ from noise alone. It was then used to choose between candidate implementations (Table~\ref{tab:ext}), so it is development data as well. Nine of its prompts repeat prompts of the first set verbatim; the combined set therefore has 230 entries and 221 distinct prompts, and we keep the duplicates so that totals match across tables. The development sets were not built from a category scheme and carry no category labels.

The \emph{held-out set} (100 prompts) was written on 14 November 2026, after the converter and the runtime were final. It has no prompt in common with the development sets, and covers eight categories: 20 factual questions, 20 explanations, 10 short creative writing tasks, 10 requests for practical advice, 10 lists, 10 arithmetic and word problems, 10 language tasks (translation, grammar, summarising) and 10 questions on programming and computing. Apple's answers were collected once and the evaluation was run once. No prompt was removed or replaced after any result had been seen, and no implementation choice was made on this set.

\paragraph{Metrics.} \emph{Teacher-forced top-1 agreement} is the primary measure. The rendered prompt and Apple's answer are fed to the reconstruction, and at each answer position we ask whether the reconstruction's most likely next token is the token Apple produced. Because Apple decodes greedily, that token is Apple's own most likely token, so the measure compares the two models' top choices given an identical context. It is not a measure of free-running output and not a measure of task accuracy. \emph{First-token agreement} is the same test at the first answer position only. \emph{Free-running identity} lets the reconstruction generate its own greedy answer (up to 300 tokens) and counts the answers that equal Apple's character for character after surrounding whitespace is removed. A single different early token changes the rest of an answer, so this measure is far stricter and is dominated by the first few tokens.

\paragraph{Token alignment.} Since the API returns text, Apple's token sequence is not observed. We remove leading and trailing whitespace from Apple's answer, tokenise it with the reconstructed tokenizer without interpreting special tokens, and append the end-of-turn token. The scored positions are these tokens: the first is predicted from the last token of the rendered prompt and the end-of-turn token from the last answer token. Prompt tokens and role markers are not scored. This assumes that Apple's model emitted the canonical tokenisation of its answer. The assumption cannot be checked directly; the tokenizer reproduces Apple's token counts on 81 of 81 test texts (Section~\ref{sec:fidelity}). No reference answer in any set was empty, truncated by an error, or a guardrail refusal.

\paragraph{Unit of analysis and uncertainty.} Tokens of one answer are correlated: they share a prompt, a routing decision and a context. Treating the answer tokens as independent trials would understate the uncertainty, so the unit of resampling is the prompt. Confidence intervals are 95\% percentile intervals from 10{,}000 bootstrap resamples of prompts~\cite{efron1979bootstrap}, with token-level agreement recomputed on each resample. We also report the distribution over prompts (median agreement and the number of prompts on which every token agrees) and absolute counts.

\paragraph{Development and held-out results.} Several implementation choices were made by agreement with Apple on the development sets: the prompt template, the layer-0 input, the routing schedule, the Neural Engine SiLU table and the treatment of the input bias at re-pick tokens. Each also has independent support in Apple's code or program, but scores on prompts that guided those choices can overstate agreement on unseen prompts. The held-out set exists to measure that, and Section~\ref{sec:fidelity} reports it first.

\paragraph{The layer-0 input: no multiplier, and a bias only for generated tokens.} An initial analysis fitted an input multiplier $k$ and found the score flat for $k=8$--14. That scan was invalid: llama.cpp's generic embedding code already applied the GGUF's \code{embedding\_scale}, and the AFM graph applied it again, so the scan really covered $k=80$--140. Dumping llama.cpp's intermediate tensors and comparing them with an independent NumPy forward revealed a factor of exactly 10 at the layer-0 input. Scanning the true multiplier with the expert picks held fixed gives a sharp optimum at $k=1$ (mean log-loss of Apple's tokens 0.140, against 0.143 at 0.75 and 1.25 and 0.240 at 100). This agrees with Apple's program: the embedding gather has no multiply.

With $k=1$ the body of the network and the router disagreed. The body wanted the input bias added, but the router's picks were best when the bias was negligible. This was established by computing the picks from a forward at a larger $k$, or with the bias removed; a version that changed only the layer-0 attention balance did not help (78\%). Apple's ANE program has two procedure families. The prompt procedures (\code{prompt\_opt}) add a zero constant at layer 0. The extend procedures, which compute generated tokens, add the bias vector. Applying the bias to generated tokens only is one consistent model for both parts. It reaches 95.9\% with the picks held fixed and 96.1\% in the llama.cpp runtime, which gives the bias to single-token decode steps and not to prompt chunks. Flipping the bias's sign costs two points, so the vector is genuine; it belongs to one procedure family only.

\section{The remaining gap}\label{sec:open}
%======================================================================

The prompt template, the expert schedule, the layer-0 input and the activation function follow Apple's code and program. On the first development set 37 of 1127 answer tokens still differ, and on the combined development set 316 of 6572; Apple's token is almost always our second or third choice. We regard the arithmetic of Apple's compiled program as the leading explanation of this residual, and this section sets out the evidence for and the limits of that view. Attributing a residual gap to numerical noise requires care: before the layer-0 corrections a gap of eight points could be, and was, mistaken for a noise floor. The following were therefore measured directly:
\begin{enumerate}
\item \textbf{The ANE's matrix multiplies are accurate.} We ran our own CoreML programs on the Neural Engine, confirming the device with Core ML's compute plan. Sums accumulate at high precision and only the fp16 output is rounded (relative error $2.8\times10^{-4}$, the same as fp32 accumulation with an fp16 result). The low-precision accumulation one first sees comes from Core ML's fp16 CPU path, not the ANE.
\item \textbf{Its SiLU is a 33-knot piecewise-linear table} (knots every 0.5 on $[-8,8]$, fitted values, for example $0.2964$ at $x=0.5$ where SiLU is 0.3112). The same 128-byte table appears 2113 times in AFM's ANE program, once per FFN task, and it is the program's only activation table. We tabulated it for all 65\,536 fp16 inputs. It is exactly linear interpolation between the knots, with a left tail clamped to zero below $-10.2$ and $x-0.0039$ above 8, rounded to fp16. With the uncorrected layer-0 input, emulating it is neutral (10 fixed, 8 broken) because the layer-0 error dominates. On the corrected model it fixes 14 and breaks 5 tokens (96.10\% $\to$ 96.72\%), so it is the default. Its softmax, exp and rsqrt are also approximate (0.3--0.4\% relative error).
\item \textbf{Apple's speculative decoding is exact.} Every FM-API adapter sets \code{draft\_soft\_match\_tolerance} to 0 and turns rejection sampling off, so the draft model never changes a greedy token. The FM-API adapter is the declared-empty adapter (signature = SHA-256 of the empty string), and there is no repetition penalty.
\item \textbf{The router is robust to arithmetic.} Computing it with fp16 accumulation moves 0.01 of 23 experts per layer-pick, and random noise strong enough to swap a third of an expert per layer changes 2\% of predictions without moving the agreement.
\end{enumerate}
Every weight, gain, bias, the router, the tokenizer, the template and the routing rule come from Apple's files and code; nothing was trained or fine-tuned.

\paragraph{Path noise.} On the corrected model, the CPU and Metal backends (identical mathematics) disagree on 0.71\% of answer tokens (8/1127), and their agreement with Apple is identical (96.72\%). The remaining 37 misses are near-ties: Apple's token is our second choice in 84\% and always in our top three, and the median logit gap is 0.40. Rounding every matmul output to fp16, as the ANE stores it, gives 96.89\% (within noise). With the uncorrected layer-0 input, mathematically identical variants disagree on 0.1--2.4\% of next-token choices: fp16-rounded activations against fp32, llama.cpp's RoPE kernel against an elementwise one, or one batch against a prompt batch followed by single steps. The 2-bit weights and the int8 KV cache amplify rounding, so a percent or so of residual disagreement is expected even from an exact model.

\paragraph{A larger test.} The 40-prompt set moves by about $\pm0.4\%$ from noise alone, so we added 190 prompts (6572 answer tokens in all) and re-ran every candidate (Table~\ref{tab:ext}). The Neural Engine SiLU is worth a full point. Every other ANE detail we could emulate is neutral: fp16 matmul outputs, int8 KV on or off, keys quantised before their gain, and fp16 RoPE tables. Truncating instead of rounding the int8 cache costs a point, so Apple rounds to nearest. Of the 316 misses of the reference row, 2.9\% of tokens are missed under any routing and 1.9\% only under Apple's schedule. The latter is consistent with our prompt-level pick differing from Apple's by a boundary expert or two: the 23rd and 24th router logits are a median 0.003 apart, about the size of a rounding difference in the layer-12 state. Apple's log also confirms the re-pick timing. Around a boundary the runtime steps one token at a time, and the pick at position 96 uses token 96 itself. Apple's fp16 logits never tie at the top, and its softmax errors (about 0.2\% in the denominator) cancel in the post-attention RMS norm.

\paragraph{Running the dense layers on the Neural Engine.} As a direct test of the arithmetic, we rebuilt layers 0--11 as a Core ML program, which placed every operation on the ANE: int8 KV round and clip, the ANE's own SiLU and softmax. We fed its layer-12 state to llama.cpp for routing and the remaining 44 layers. The state differs from our emulation by about 15\% (relative norm) after 12 layers; in isolation each layer's FFN agrees with our SiLU-table model to fp16 rounding (0.5\%), and int8 steps in the very coarse layer-0 values amplify the differences. Agreement with Apple stays the same: 94.92\% against 95.19\%, but 224 of 6572 tokens flip (103 fixed, 121 broken). The control, the same program in fp32 on the CPU with exact SiLU, gives 94.42\%. So two plausible versions of the hardware arithmetic disagree on about 3.4\% of tokens without either being closer to Apple, which is the size of the remaining gap. Core ML compiles our graph differently from Apple's own ANE program, so even the real hardware does not reproduce Apple's rounding.

\paragraph{Interpretation.} These experiments make compiled-program arithmetic a plausible dominant contributor to the remaining disagreement: equally defensible versions of the arithmetic differ from one another by as much as the reconstruction differs from Apple, and the misses are near-ties. They do not exclude a smaller contribution from routing or execution details that cannot be observed. Two such candidates are a prompt-level expert pick that differs from Apple's by a boundary expert (about 1.9\% of tokens are missed only under Apple's schedule, see above) and behaviour of Apple's runtime between requests that our single-request tests do not exercise. Distinguishing these would require either Apple's per-layer expert lists, which the log redacts, or an execution of Apple's own compiled program on chosen inputs, which the operating system does not permit to third-party processes.

\paragraph{Apple's own expert decisions.} Apple's runtime logs every pick per layer (``layer $N$ experts: \dots''). The expert list is marked \emph{sensitive}, so it stays redacted even with a logging profile that enables private data for the inference service. That profile does reveal the subsystem's ordinary private values. The cache statistics are public, though. At each pick the runtime logs \code{reordered}, \code{replaced} and \code{loaded}, and within one answer the cache holds exactly the current pick, so \code{replaced} at a re-pick counts the experts that changed. Over the 135 re-picks in the 230-prompt set, our router's predicted churn tracks Apple's with $r=0.934$ and a mean miss of 4.6 of about 40 changed experts. This indicates that our picks differ from Apple's by at most a few of the 1012 per pick, with the caveat that the log counts changes and does not identify experts. Moving the re-pick to a neighbouring token makes the match clearly worse (5.3--5.4), which supports the schedule. Every arithmetic variant scores the same within noise: 4.50 for the ANE-computed layer-12 state, 4.60 for the default, 4.60 for fp16 matmul outputs, 4.65 for fp32 with exact SiLU, 4.67 for exact SiLU, and 4.45 without the input bias at re-pick tokens. Apple's re-picks change slightly fewer experts than ours (by 1.6 on average). A small preference for already-loaded experts fits the counts only marginally better (4.60 to 4.40) and lowers agreement (95.15\%), so we reject it. Apple's code runs a dense-only function at each re-pick token, the same procedure family as the prompt, which adds no layer-0 bias. Dropping the bias at those tokens raises agreement from 95.19\% to 95.27\% (12 fixed, 7 broken) and is part of the default. Between prompts the counts do not track the previous prompt's pick (Apple 501 on average, our prediction 111), so the cache is not simply carried over between requests.

Further numerical and schedule experiments, run on an earlier configuration, are collected in Appendix~\ref{sec:uncorrected}; they agree with the findings above.

\section{Apple Intelligence feature adapters}\label{sec:adapters}
%======================================================================

Sections~\ref{sec:adapters}--\ref{sec:pico} cover the components that ship alongside the main model. Each is decoded by the same methods, but the available validation differs from one to the next, as Table~\ref{tab:companion} records.

Apple Intelligence features ship as rank-48 LoRA adapters~\cite{hu2021lora} for this backbone: 26 on the test machine, covering summaries, proofreading, mail replies, smart replies, translation, message actions, reminders, Image Playground suggestions, Photos memories, dictation and others. Each asset holds \code{lora\_i}$N$\code{\_r48\_48\_constant\_data.bin}, where $N$ is the IFP level the feature runs at. Its metadata holds Apple's prompts for the feature (system instructions and content templates, in the \code{afm\_cider\_v2} format) and the same backbone signature as the base model. All of them carry the empty-input SHA-256 as their ``adapter signature'', so that field says nothing about whether an adapter is trained. The FM API's own adapter is untrained (B RMS $3\cdot10^{-5}$), while the feature adapters are trained (B RMS $2\cdot10^{-3}$ to $3\cdot10^{-2}$).

\paragraph{Layout.} A file holds 218 (A, B) pairs as fp16: A as $[48,\text{in}]$, then B as $[\text{out},48]$. The pairs come in the order of the package manifest, which sorts the tensor names as strings: the dense segment (o, q, k, v, \code{linear\_0}, \code{linear\_1}, down) $\times12$, then kv-reuse (o, q) $\times21$, then standard sparse (o, q, k, v) $\times23$, with the layers inside each segment in the order 0, 10, 11, 1, 2, \dots{} rather than numerically. \code{linear\_0} is the gate and \code{linear\_1} the up projection, and the adapter is applied at scale $0.5$. All three points match the 300M adapters (Section~\ref{sec:pico}).

\paragraph{Checked against Apple.} Apple's public Translation framework is served on device by the \code{machine\_translation} adapter at ifp1 (the model manager's log names the asset, and the request produces speculative-decoding log lines), and its output is deterministic. The prompt is not in the adapter metadata. We recovered it from the \code{TranslationInference} framework and confirmed it with the token counts Apple logs for each request (51, 61, 63 and 65 tokens for four probes, all reproduced): the system turn is \emph{``Conversation between a user and a friendly assistant. You are an expert translator.''} and the user turn is \emph{``Translate from $S$ to $T$.\textbackslash n$S$ phrase: \emph{text}\textbackslash n\textbackslash n$T$ phrase:''}, with language names such as ``American English'' and ``Chinese, Traditional''.

On 200 translations of 40 English sentences into German, French, Spanish, Japanese and Traditional Chinese, teacher-forced on Apple's output, our adapter picks Apple's token at 3{,}380 of 3{,}424 positions (98.7\%); the base model at ifp1 without the adapter reaches 89.2\%. Table~\ref{tab:translation} gives the figures by target language; the adapter's contribution is largest for Japanese and Chinese, where the base model alone is weakest. Free-running in llama.cpp, 166 of the 200 translations are identical to Apple's. Apple translates each sentence of a multi-sentence input separately, which our test did not do. The reference is essential. An alternative decode (numeric layer order, scale 1, \code{linear\_0} = up) passes a likelihood test on a small set of self-constructed proofreading pairs, yet scores 0.7\% against Apple's translations: a decode of this kind helps slightly at a small scale and diverges at full scale. Writing Tools' Proofread action cannot serve as a reference, because it is served by a Private Cloud Compute model.

\section{The speculative-decoding draft model}\label{sec:draft}

Apple pairs the model with a small draft model for speculative decoding~\cite{leviathan2023speculative}: asset \code{fm\_api\_generic.draft}, \code{model\_config} \code{v11-ifp-9m}. We separate two questions that carry different certainty: what the asset encodes (the draft model's weights and graph, read from its program) and what Apple's runtime does with it (the speculation procedure, inferred from logs). Its metadata asks for 7 draft tokens per step, exact matching (\code{draft\_soft\_match\_tolerance} 0) and no adaptive length. The asset has no weights file: everything is inside its Neural Engine program (\code{binary\_0.hwx}, 22 procedures: 3 readouts of 8/16/64 tokens and 19 \code{extend} variants) and its \code{program.odix}.

\subsection{What the asset encodes}
\paragraph{Reading the dataflow.} The 132 weight convolutions (11 per layer) are the tasks with Neural Engine opcode \code{0x46} and a kernel offset. Their roles follow from the surrounding tasks. In layers 1--11 the first 128-channel projection is written straight to the cache by a tile-destination DMA, so it is $V$. The second passes through RoPE, a 32-wide RMS reduction and a gain multiply before its cache write, so it is $K$. Layer 0 orders them $q, k, v$. The attention score scale $1/\sqrt{32}$ sits in the QK matmul's output-scale register, and the softmax is an exp2 with a $\log_2 e$ prescale. The 768-wide FFN hidden is laid out by L2 address: the three up and three gate tiles are written to descending addresses, so the hidden is $[\text{tile}_2 \mid \text{tile}_1 \mid \text{tile}_0]$. In the last layer the compiler re-banks these buffers and leaves one destination register implicit, so we use the conv order there. Norm gains come from \code{\_\_TEXT,\_\_const}, one 0x4000-byte block per procedure, addressed by the tile-source offsets. In layer 2 the query gain multiply reuses the tile the key gain loaded; the compiler had merged the two. The query and key gains of a layer agree up to sign flips inside rotation pairs and a few ulps, so the norm cannot be moved before RoPE. The final norm computes $\mathrm{rsqrt}(\mathrm{mean}((0.1x)^2)+1.19\cdot10^{-7})\cdot0.1$, an fp16 overflow guard equivalent to $\epsilon=1.19\cdot10^{-5}$.

\paragraph{Validation.} A NumPy forward of this description predicts Apple's own next answer token (from the 3B model, teacher-forced) 42.95\% of the time on the 40 prompts (1127 tokens) and 37.7\% on the 230 (6572 tokens). Every alternative tested collapses: cyclic instead of unit-blocked output rows 0.0\%, reversed RoPE direction 16.7\%, query head $h\to$ KV head $h \bmod 4$ 6.7\%, $K$ and $V$ swapped 1.5\%, FFN tiles in conv order 2.3\%, raw codes without $s$ 0.3\%. The input scale is a sharp optimum at 1 (0.25: 27.6\%, 4: 36.5\%). The ANE SiLU table changes nothing (42.95\% either way). Simulating a 7-token chain with exact match, the draft's proposals are accepted 0.61 tokens per step on the 230 prompts, so each target call yields 1.61 tokens.

\subsection{What Apple's runtime appears to do}
\paragraph{The evidence.} Apple's draft program does not run from our process, but Apple's runtime reports what it did. After every output token the inference service logs running totals (\code{log stream}, subsystem \code{com.apple.tokengenerationinference}, category \code{SpeculativeDecode}): \code{countTotalAcceptedDraftTokens}, \code{countTotalRejectedDraftTokens}, \code{speculatedComputedCount}. A rise in the first at output token $n$ means Apple's draft had proposed token $n$; a rise in the second means it had not. That is one bit about Apple's draft per decision, at a known position in a token sequence we also have. Read as a greedy chain the bits did not fit: Apple accepted 53\% of the decisions where our draft's top token was right only 40\% of the time, and the two agreed on 78\%. The counters never speculate deeper than two tokens, the draft's programs take 8 tokens, the metadata sets \code{draft\_steps} to 7 and \code{draft\_use\_maximum\_likelihood\_tree}, and when Apple accepted, the token was among our draft's five best in 97.5\% of the cases with a sharp edge after the fifth.

\paragraph{Competing hypotheses.} We considered three accounts of the procedure. (a)~A greedy chain of 7 draft tokens, the usual scheme: rejected by the figures above (acceptance 53\% against 40\%, agreement 78\%). (b)~A maximum-likelihood tree, as the metadata flag suggests, with 7 nodes. (c)~The same with 6 or 8 nodes. Hypothesis (b) fits best: each round scores the last real token and 7 draft nodes, the 7 most likely nodes of a depth-2 tree by joint probability, and a token is accepted if it is a node at its level. Replaying that tree with our draft on Apple's answers (60 prompts, 1435 logged decisions, 1331 of them more than one token away from a program switch, see below) gives the same decision as Apple's draft in 95.6\% of the cases, with the same acceptance rate (55.7\% against 55.9\%); a tree of 6 or 8 nodes misses the acceptance rate (53.6\%, 57.3\%), and an unrelated model with that rate would agree 51\% of the time. The remaining disagreements are near-ties: where the token's joint probability is within a factor $2^{1/4}$ of the tree's threshold the two agree 60\% of the time, beyond a factor 2 they agree on 99.2\% (1134 decisions), beyond a factor 4 on 99.7\% (951). The GGUF run by llama.cpp gives the same greedy decisions as the NumPy forward on all 1435.

\paragraph{Limits of the identification.} The log yields one bit per decision. The tree is the simplest procedure we found that is consistent with the metadata, the depth of speculation and the acceptance rate, and under it our draft reproduces Apple's decisions wherever they are not near-ties. That is strong evidence that the decoded draft model is correct, since a wrong model would not reproduce the decisions under any procedure we tried. It is weaker evidence for the exact tree construction: other procedures with the same acceptance set at depth 2 would be indistinguishable from it in this log.

Two details of Apple's runtime are visible as well. When the sequence reaches 96 or 128 tokens the runtime moves to the next larger fixed-context program, and that round is logged as rejected whatever the draft proposed (36 such rejections of tokens our tree contains); the 104 decisions within one token of those lengths are therefore left out. And the gain of Apple's scheme is larger than a chain's: 0.56 of the tree's decisions are accepted.

\subsection{In llama.cpp}
\code{afm2gguf.py -{}-draft} writes the draft as architecture \code{afm-draft} (61\,MiB): the codes as Q4\_0 with $d=1$ (exact), $s$ as \code{token\_embd\_scale} and \code{output\_scale}, F16 projections (palette values are fp16), and an \code{output.bias} of $-\infty$ outside the draft vocabulary. The bias matters: the best draft logit is negative at about 1\% of positions, so zero rows would sometimes win. On Metal, its logits match the NumPy reference to 0.03.

Speculative decoding places a requirement on the target graph. A verify batch [last token, 7 draft tokens] is several tokens of one sequence, which would otherwise be treated as a prompt chunk: one shared expert pick, persisted, and no input bias. Verify batches are therefore recognised (every token requests logits and the run does not start at position 0) and processed exactly as single decode tokens: input bias except at re-pick positions, and routing on the latest re-pick token at or before each token. Draft tokens can be rejected after they have re-picked, so the routing state keeps two picks per sequence, each tagged with its source position. A pick from a position the batch starts at or after belongs to rolled-back tokens and is ignored. With this handling, 8-token verify batches reproduce one-token-at-a-time decoding to $2\cdot10^{-5}$ in the logits.
\paragraph{Lossless, but not faster in llama.cpp.} With greedy sampling, 7 draft tokens and no confidence cutoff (Apple's settings), \code{llama-server} with the draft returns exactly the plain answers on all 40 prompts, on Metal and on the CPU, and the plain answers are unchanged by the patch. About 11\% of drafted tokens are accepted, as the simulation predicts. Speculation is nevertheless slower in llama.cpp. Measured back to back, it was 2.1$\times$ slower on Metal and 3.5$\times$ slower on the CPU (1.8$\times$ with 3 draft tokens). A verify batch costs several single decodes here, because the 2-bit expert matmuls are compute-bound and every draft step has a fixed per-call cost. Apple's Neural Engine runs fixed-shape 8-token \code{extend} programs, so a verify step costs about as much as one token, and 0.6 extra tokens per step is a real gain there. \code{tools/eval/speculative.py} reproduces these measurements.

Images reach the model through a separate asset, \code{instruct\_3b.image\_encoder} (\code{model\_cls\_name} \code{ImageTokenizer}). It holds one Neural Engine program with six procedures, one per patch count $N\in\{1152,1728,2304,3600,4608,5760\}$, and \code{swift\_preprocess\_weights.bin}. The program's inputs are the patches $[N,3,14,14]$, an additive position embedding $[N,1024]$, RoPE rotation matrices $[N,32,2,2]$ and an additive key mask. Its output is $N/9$ embeddings of width 1536, which the 3B model reads between \code{<start\_of\_image>} and \code{<end\_of\_image>}. Apple's runtime log names the sizing rule: the aspect ratio is kept, the image is scaled to at most 338\,688 pixels (1728 patches), and both sides are snapped to multiples of the 12-patch attention window.

\paragraph{Evaluation data.} The image tests in this section use 13 images: seven photographs between $640\times480$ and $4096\times2160$ pixels, and six synthetic $672\times504$ or $504\times672$ images (a coloured square, circle and triangle, the word ``HELLO'', an arithmetic expression and coloured stripes). Apple's reference caption for each is its greedy answer through the public API, which accepts an image attachment, with the instructions used throughout. Per-token cosine similarities compare our encoder's output with the output of Apple's encoder for the same pre-processed input, token by token. Thirteen images make a check, not a benchmark, and we give no uncertainty estimates for them.

\paragraph{Reading the weights.} The int4 blocks resemble the 3B model's, but the header length depends on the convolution's flags: a 16-entry fp16 LUT, 32 zero bytes, the row scales, and the row biases \emph{only if} the convolution has a bias (Neural Engine register 1, bit 0x10). A 128-byte activation table precedes all of this when the convolution applies an activation (bit 0x20000). A fixed 128-byte header is correct only for 16-row blocks with a bias; under that assumption every bias-free block (all FFN and merger weights) is read 4 to 12 inputs out of place, with its last inputs taken from padding. The block sizes look the same either way because each unit is padded to 64 bytes. Compiling known weights with Apple's compiler settles the question: a 9216$\to$128 projection, a bias-free up projection and a SiLU-gated projection decode exactly with the flag rule and at chance level (6\%) with the fixed header.

The effective bias is the stored bias times the row scale, and times $2^{e-32}$ when the convolution's task writes the Neural Engine bias register \code{NEBias} with exponent field $e$ (its value field is 0). In this encoder only the $V$ convolutions of layers 18 and 19 do so ($e=31$); missing it left their biases twice too large, which costs 0.001--0.007 of agreement with Apple's encoder. Projection tiles are written to descending addresses, so channel order is the reversed tile order. The weights are split over two kernel sections; each block is assigned to the section where its LUT is valid. That rule is unambiguous for 1293 of 1297 blocks, and the remaining 4 follow their neighbours.

Norm gains are $[\text{bias}\mid\text{scale}]$ constant tiles that the planar engine fetches; we take every gain from its fetch offset rather than from a layout formula, because the global-attention layers use a different constant layout. The compiler also folded a $0.01$ pre-norm scale into the encoder: the last residual add scales its residual operand by $0.01$ (a planar-engine operand scale, the same register that holds $1/8$ in the global layers), and $0.1$ is folded into each of the last layer's up and down projections, which are ten times smaller than every other layer's. The converter undoes this. Activations are 33-knot piecewise-linear tables: SiLU on $[-8,8]$, GELU on $[-4,4]$, with explicit linear tails.

\paragraph{Ground truth from Apple's own encoder.} Unlike the language model, the encoder's MPSGraph executable runs on the Neural Engine from our own process (about 0.8\,s per call), so Apple's encoder is a direct oracle for any input we build. A copied package does not load (``Program load failed''), so weights cannot be patched to bisect. We therefore used constructed inputs. When all $N$ tokens are identical, every attention layer returns $V$, so the encoder becomes a per-token function of one 1024-vector; and the merger can be inverted from the output. With the fixed header the inversion stalls at cosine 0.991 for every seed; with the flag rule it reaches 0.99999. The NumPy forward then matches Apple's output at cosine 0.987 on constant-token inputs and 0.95--0.97 per token on real images. One further correction is invisible to constant-token inputs: layer 0 emits its key projection before its query projection. With $q$ and $k$ of layer 0 exchanged, the match on real images rises to 0.98--0.99 per token. The llama.cpp projector requires two further measures to follow: Apple's activation tables in place of the exact SiLU and GELU (with exact activations it matches Apple's encoder at 0.975), and an antialiased bicubic resize, since a plain 4-tap bicubic aliases when a large photo is reduced (0.84 against Apple's encoder for a $4096\times2160$ photo, 0.985 with antialiasing). From the image files the projector matches Apple's encoder at 0.98--0.99, its Metal and CPU paths agree to 0.9999, and 6 of 13 free-running captions are identical to Apple's.

Every wiring choice that can be varied has a sharp optimum: the alternative $V$/$O$ and gate/up/down pairings score 0.16--0.23, and in every layer each other choice of $V$ group is worse; on a real image, swapped $q/k$ scores 0.09, half-split RoPE pairs 0.50, $x$-before-$y$ 0.51 and transposed patches 0.85. Fitting per-layer branch scales gains less than 0.4 points, so the remaining percent is not a wiring error. A Core ML replica of our forward run on the Neural Engine was less faithful still (0.76), so the numerics of Apple's compiled program are the most likely source of the remaining difference.

\paragraph{Through the 3B model: the RoPE layout.} Our prompt places the question, a newline and the image in the user turn, 266 tokens in total, exactly the count Apple's runtime logs for the same request. Several things the encoder program cannot tell us are chosen by Apple's host code: the pixel normalisation, the position table's interpolation, and how the 32 RoPE rotations of a head are split between the row and the column. Comparing against Apple's encoder cannot settle these, because both encoders receive whatever inputs we build. The 3B model's behaviour can, indirectly (Table~\ref{tab:preproc}). With the obvious layout (row on pairs 0--15, column on 16--31) the language model received colours and scene gist but no geometry. Shuffling the 192 image tokens hardly changed anything, and asked whether a red circle is left or right, top or bottom, it answered ``Left'' and ``Top'' for all four pictures, where Apple's model answers all four correctly.

The correct layout \emph{alternates}: pair $2f$ rotates by the row and pair $2f{+}1$ by the column, both at frequency $\theta_f$. With it all four spatial answers are right with margins of 5--12 logits. The mean log-probability of the key words of Apple's captions (circle, HELLO, equation, Golden, balloons, \ldots) rises from $-2.99$ to $-0.20$. The other host choices are then sharp: a negated rotation mirrors the image (``HELLO'' at $-8.2$), bilinear instead of bicubic position interpolation is worse ($-0.26$), and so is a transposed position table ($-0.21$). ImageNet normalisation is slightly better than CLIP's ($-0.20$ vs $-0.22$). With CLIP's statistics a plain white image is barely ``white'' (0.2-logit margin over gray, against 6.5 with ImageNet's), and CLIP's mean vector does not occur anywhere in the operating system's shared cache.

\paragraph{Decoding.} The model is read as the draft model and the image encoder are: from the Neural Engine task stream rather than from symbol names. Five properties of the format are essential, several of them shared with the image encoder; a decode that misses them recovers every tensor yet produces no text. (1) The int4 header is 96 bytes (LUT, 32 zero bytes, 16 row scales; the bias flag is clear), followed by the codes and 32 bytes of zero padding; an assumed 128-byte header shifts every input axis by 4 positions (12 for the 128-row blocks). (2) The norm gains are not folded away: the planar engine fetches all 97 of them (four per layer and a final one) from \code{\_\_TEXT,\_\_const}, beside a $[0\mid s]$ tile that scales the hidden state before the readout and the $-40000$ vocabulary mask. (3) The embedding is a plain 8-token interleave starting at the data section; an apparent lane ``skew'' and 4-row shift are artefacts of a wrong base address. (4) The per-layer multiplier (9.5--12.0) applied with the key gain is not a temperature. It is the int8 scale of the key cache, and the $q\!\cdot\!k$ matmul's own fp16 scale register divides it back out: their product is $0.1250$ in all 24 layers. Values are likewise stored in int8 (scales 305 down to 10.5) and rescaled in the attention-times-$V$ matmul. (5) The two 256-wide projections are emitted in different orders: layer 0 computes $K$ first, every later layer $V$ first, as in the draft model. We assign them by dataflow: $K$ is the one whose output passes through RoPE and the head norm. Block order within a tensor follows the destination addresses (the query blocks and the up projection's are written to descending addresses), as for the encoder.

\paragraph{Results.} Apple exposes this model through no public API, so its outputs cannot be compared as for the 3B model. We evaluate it as a language model instead. On two passages of plain English (172 and 102 tokens) its perplexity is 38.2 and 24.6, the median rank of the correct next token is 2, and it ranks it first 29\% and 39\% of the time. On random token sequences repeated twice it copies the second half 78\% of the time, the signature of trained induction heads~\cite{olsson2022induction}. Each of these properties is necessary: with a positional $K$/$V$ assignment induction is 0\% and perplexity above 100\,000; swapping $K$ and $V$ in layer 0 as well leaves perplexity above 20\,000; halving or doubling the logits raises it threefold to ninefold, so the readout is calibrated as decoded. Greedy decoding through llama.cpp:
\begin{quote}\small
The capital of France is $\to$ \emph{Paris.}\quad Water boils at $\to$ \emph{100\textdegree C.}\\
Once upon a time, there was a little girl named $\to$ \emph{Lily. Lily was a little girl who loved to play with her toys}\ldots\\
(chat turn) What is 12 plus 7? $\to$ \emph{12 plus 7 is 19.}\quad Write one sentence about the ocean. $\to$ \emph{The ocean is a vast, mysterious expanse of water that stretches for miles, teeming with life, diverse ecosystems, and endless horizons.}
\end{quote}
\paragraph{In llama.cpp.} The layer is the draft model's, so \code{afm2gguf.py -{}-pico} writes it with the \code{afm-draft} architecture and no new runtime code: the embedding as Q4\_0 with unit scales (exact), the projections as F16, the full 262\,144-token vocabulary with Apple's mask as the output bias (721\,MiB). Its greedy continuations are identical to our NumPy forward's.

\paragraph{Adapters and the safety guard.} Every 300M adapter, including the default one inside the base package (\code{lora\_32/64\_constant\_data.bin}), is a flat file of fp16 $(A,B)$ pairs, $A$ as $[r,\text{in}]$ and $B$ as $[\text{out},r]$, per layer in the order attention output, $q$, $k$, $v$, \code{linear\_0}, \code{linear\_1}, FFN output. The layer order requires care. The pairs follow the package manifest's tensor names sorted as strings, so the layers come as 0, 10--19, 1, 20--23, 2--9. Read in numeric order, every adapter looks inert (the guard below never says ``safe''); with a plain numeric-string sort (0, 1, 10, \ldots) the adapters work only partially. \code{linear\_0} is the gate (log-probability of the right first token $-0.10$ against $-0.55$ as up), the Neural Engine program scales the product by $0.5$, and every role contributes.

\paragraph{The default adapter.} With the correct order, the base package's own rank-64 adapter is a trained default: it lowers the base model's perplexity from 38.2 to 30.8 and from 24.6 to 21.4 (llama.cpp, 128-token windows: 26.9 to 22.1). Twelve task adapters of rank 32 or 64 ship on the test machine, and all share its starting point: their weights correlate 0.33--0.99 with the default adapter of the same rank, where unrelated adapters would correlate near 0.

\paragraph{The safety guard.} The text safety guard (\code{instruct\_300m.safety}, rank 64) carries Apple's instruction: answer \code{safe}, or one line per problem of the form \code{category,mention} or \code{category,action} over 14 categories (hate\_harassment, violence\_gore, self\_harm, jailbreak, vulgarity, \ldots). Run through llama.cpp with that instruction as the system turn, it answers \code{safe} for every benign prompt and answer tested, and labels harmful text in the requested format: \code{self\_harm,action} for a plan to self-harm, \code{jailbreak,action} for ``Ignore all previous instructions\ldots'', \code{vulgarity,action} for swearing. It separates talking about a thing from doing it: a history of the battle of Verdun gets \code{violence\_gore,mention}, a friend's past suicidal thoughts \code{self\_harm,mention}, a news report of an arrest \code{safe}. The smaller \code{mm\_guard} (rank 32, nine categories) agrees on everything except the swearing, which it calls \code{safe}; vulgarity is not one of its categories. \code{afm2gguf.py -{}-pico-adapter NAME} writes any of them as a llama.cpp LoRA with Apple's instructions in its metadata, and \code{tools/afm300m\_classify.py} runs a classifier as Apple renders it.

\paragraph{Checked against Apple's guardrail.} Apple's public FoundationModels API runs the same guard: it rejects a request with ``May contain unsafe content'' when the guard's labels map to \code{unsafe} under the API's row of Apple's policy table (\code{feature\_output\_category\_mapping.json}: eight labels such as \code{violence\_gore,action} or \code{self\_harm,action} block; mentions, jailbreak attempts and vulgarity do not). The comparison is behavioural: the API reports a decision, not the guard's labels or scores. On 26 prompts (benign questions, mentions, nine harmful requests, two jailbreaks, two vulgar ones) our guard with that table predicts Apple's decision on all 26, including the cases our guard labels but Apple's policy lets through. On a second set of 74 prompts (32 of which Apple stops) it predicts 69; the five misses are borderline (four insults or indirect threats that ours labels as an action and Apple lets through, and a hobby question about lock picking that Apple stops), so 95 of 100 in all. One request Apple stopped at its output check (``Response may contain sensitive\ldots''), which our guard already flags on the input.

\paragraph{The image encoder.} The 300M model has its own image encoder, \code{instruct\_300m.\allowbreak image\_tokenizer} (\code{ImageTokenizer}, model id \code{afm-plus-v11-300m-instruct-4bit-pal}). Its program has the 3B encoder's structure exactly: 24 layers, windows of $12\times12$ patches with full attention in layers 7, 15 and 23 (counted from the attention matmuls per layer), the same $3\times3$ merger, and a last projection to 1024 instead of 1536. Its position table differs, so it was trained separately.

Three details differ from the 3B encoder. The weight palettes are sorted real-valued codebooks rather than integers; there is no folded $0.01$ scale (the last layer's weights are in line with the others); and 15 of its 96 attention bias tensors come from tasks that write the \code{NEBias} exponent ($e=28$--31), so their biases are $2^{e-32}$ times the stored value. Read without that factor they are 2--16 times too large, which no weight statistic reveals but Apple's own encoder does: on identical inputs the agreement is cosine 0.45--0.54 per token without the factor, and 0.61--0.78 on photos and 0.97 on constant inputs with it. Two further corrections, both checked against Apple's encoder, bring it to 0.68--0.87: layer 0 emits its key projection before its query projection (as in the 3B encoder), and the five final-norm gains that are fp16 subnormals are taken as zero.

\paragraph{The merger normalisation.} The remaining discrepancy is a single layout property of the merger. Its normalisation is a depthwise convolution whose kernel holds a (bias, gain) pair per channel in 16 units of 256 pairs, and the units are \emph{interleaved} over the channels: channel $c$ is entry $\lfloor c/16\rfloor$ of unit $c \bmod 16$. Reading the units one after another puts every gain and bias on the wrong channel. Nothing in the bytes indicates this, and the 3B encoder is nearly insensitive to it (0.992 to 0.994 on constant inputs), because its gains and biases are nearly uniform; the 300M encoder's are not. It was identified with constant-token inputs, where Apple's encoder is a per-token function: the reconstruction's output was uniformly 17\% too small in norm, the 3B encoder's was not, and refitting only the 4096 biases of that layer on 54 inputs raised held-out agreement from 0.956 to 0.997, and on photos (never fitted) from 0.68--0.87 to 0.95--0.97. The fitted biases correlated with the stored ones only under the transposed unit order. With that order and no fitted quantity the 300M encoder agrees with Apple's at 0.998 on constant inputs and 0.990--0.999 per token on photos (the 3B encoder: 0.989--0.997), and llama.cpp's projector at 0.98--0.99 from the image files.

The two programs were also compared register by register: they are identical task for task except for the bias exponents, the folded $0.01$, and the output width, and every weight block and bias tensor of one correlates with its counterpart in the other ($r\approx0.98$ for weights, slope $1.00$ for all 96 bias tensors under the exponent rule). The same rule explains every one of the 96 tensors' power-of-two ratio to the 3B encoder's biases. The same decoder therefore covers both (\code{afm2gguf.py -{}-pico-vision}); the 3B projector it writes is unaffected.

\paragraph{Image classifiers.} In llama.cpp the encoder runs as the existing \code{afm} projector. The only runtime requirement is that the \code{afm-draft} graph apply the per-dimension embedding scale to text tokens only, so that image embeddings enter unscaled. With the default adapter the 300M model describes images (``The image contains the text ``HELLO'' in a stylized font.''; ``a blue square with a white background''). The image classifiers are adapters of the same kind as the guard: \code{misc\_safety} holds Apple's instructions for violence/gore classification and for counting people (``0, 1, 2''), and \code{prepubescent\_safety} checks for children shown with adult features. On stock photos from Keynote's themes the people counter answers 0 for all four photos without people, 1 for all five single portraits (without the bias rule it misses a person whose face is hidden by a hood), 2 for two women, and 2 for three boys, where 2 is the largest answer allowed. The two safety classifiers answer \code{safe} for every benign image tested, including synthetic red paint splatter; they were not tested on harmful images, so nothing can be concluded from this about their safety performance.

The following were excluded as causes of the residual difference between the two encoders: the Neural Engine's softmax (its 33-knot $2^x$ and $2/m$ tables and fp16 $\log_2 e$), fp16 saturation in the norms, reduced-precision palettes, and the kernel-section choice of the three blocks that are valid in both sections; none changes the agreement. Apple's encoder is also numerically stable: perturbing an input by $10^{-3}$ moves its output by less than 0.001 in cosine.

\section{Limitations}\label{sec:limits}
%======================================================================

\paragraph{What the primary measure does and does not show.} Teacher-forced agreement with the public API measures how often two models share a top choice given an identical context. It is not parameter-by-parameter execution equivalence, and it is not task accuracy. Free-running identity is much lower (Table~\ref{tab:core}) because one differing token redirects an answer.

\paragraph{Unobserved internals.} Apple's API exposes neither probabilities nor internal activations, and the runtime log redacts the selected expert indices. The routing schedule is therefore validated through counts of changed experts, not through the identities of the experts, and the tokenisation of Apple's answers is assumed, not observed.

\paragraph{Numerical equivalence.} The arithmetic of Apple's compiled Neural Engine program is not reproduced exactly. We regard it as the leading explanation of the remaining disagreement (Section~\ref{sec:open}), but that is a hypothesis; a contribution from unobserved routing or execution details is not excluded.

\paragraph{Evaluation data.} The prompts are short, single-turn and English. Long contexts, multi-turn conversations, other languages (apart from the translation adapter's targets), tool calling and guided generation were not evaluated. The development prompts were used at several stages of debugging; only the held-out set is free of that. All three sets were written for this study, in a similar style, and are small by the standards of model evaluation.

\paragraph{One machine, one model version.} All results come from one M4 Mac, macOS~27.0, and one version of each asset. Apple updates its assets independently of the operating system; the formats, offsets and scheduling rules reported here may change with any update.

\paragraph{Companion components.} Only two of the 26 feature adapters have a reference. The 300M base model has none and is assessed only as a language model. The safety guard is compared with the public API's decisions, not with the guard's internal output, on 100 prompts written for the purpose; the image safety classifiers were run on benign images only. The image tests use 13 images. None of these supports a general statement about safety performance or caption quality.

\paragraph{Lossless conversion.} The equality of the converted weights with Apple's values is established by construction and by a sampled comparison of 55 million weights, not by an exhaustive one (Section~\ref{sec:weights}).

\section{Related work}\label{sec:related}
%======================================================================

\paragraph{Apple's descriptions of its models.} Apple has described its foundation language models and their adapter-based deployment in a technical report~\cite{gunter2024afm}, and the pruning method behind the sparse feed-forward network in a paper on Instruction-Following Pruning~\cite{hou2025ifp}, in which a mask predictor reads the instruction and selects which feed-forward parameters to activate. Those publications state the principles. The present work documents one shipped instance: its dimensions, its storage, the router's input and the schedule on which the selection is refreshed, none of which they specify.

\paragraph{The Neural Engine.} Apple has published guidance on structuring transformers for the Neural Engine~\cite{appleane2022}. Outside Apple, the hardware and its software stack have been documented by experiment~\cite{hollance,bryngelson2026ane}. This paper relies on the same kind of observation, applied to one compiled program: its weight encoding, constant layout and activation tables.

\paragraph{Building blocks.} The recovered architecture combines known components: RMS normalisation~\cite{zhang2019rmsnorm}, rotary position embeddings~\cite{su2021rope}, grouped-query attention~\cite{ainslie2023gqa}, SwiGLU feed-forward blocks~\cite{shazeer2020glu}, low-rank adapters~\cite{hu2021lora}, a SentencePiece vocabulary~\cite{kudo2018sentencepiece} laid out as in Gemma~3~\cite{gemma3}, a vision transformer~\cite{dosovitskiy2020vit} as image encoder, and speculative decoding~\cite{leviathan2023speculative}. The post-normalised residual of Section~\ref{sec:arch} and the cross-layer key/value reuse are, to our knowledge, not described in Apple's publications.

\paragraph{Runtime and diagnostics.} The portable implementation builds on llama.cpp~\cite{llamacpp} and its GGUF format~\cite{gguf}. The diagnostic probes follow the circuit-level analysis of transformers~\cite{elhage2021framework,olsson2022induction}: copying heads and induction behaviour serve here as tests of whether a set of decoded weights forms a working model.

We are not aware of prior public work that reconstructs this model's weights into a portable runtime and measures the result against Apple's own model.

\section{Responsible use}\label{sec:responsible}
%======================================================================

\paragraph{What is published.} We publish our own code: the llama.cpp architecture patch, the converter, the evaluation scripts and the prompt sets (\url{https://github.com/yu314-coder/afm-ifp-teardown}). The code contains no Apple data.

\paragraph{What users must provide.} The converter reads the model assets that Apple Intelligence has installed on the user's own Mac and writes the GGUF there. Without those assets it produces nothing.

\paragraph{What is deliberately not distributed.} We publish no weights, tokenizer data, decoded assets or converted model files, and no reference answers from Apple's model beyond the short quotations in this paper. The model's weights belong to Apple. We have asked Apple whether redistribution would be permitted.

\paragraph{Scope of this statement.} We make no claim about how Apple's licence terms or any law apply to running the converter or to using its output; that assessment is separate from this work and rests with each user. The safety guard and the image classifiers are documented so that they can be studied, and the tests reported here do not establish their safety performance. The project is unofficial and is not affiliated with or endorsed by Apple.

\section{Conclusion}\label{sec:conclusion}
%======================================================================

A substantial part of a proprietary on-device model can be recovered from locally installed assets and observable platform behaviour. For \code{afmplus-v11.2-ifp} this comprises every stored tensor, the computation graph, the tokenizer, the prompt template and the expert-selection schedule, and a portable runtime that executes them on macOS, Linux and Windows. The principal architectural findings are a residual stream in which both additions carry normalised values, key/value reuse across the last 21 layers, and a sparse feed-forward network whose experts are chosen once per prompt from a single token and refreshed every 32 positions.

What was validated directly is the agreement of the resulting model with Apple's own: 95.66\% of greedy next-token choices on held-out prompts under teacher forcing, with the weight layout confirmed by Apple's compiler and the prompt rendering by Apple's token counter. What remains open is exact arithmetic. The reconstruction is not numerically identical to Apple's compiled Neural Engine program, the remaining disagreements sit at near-ties, and whether arithmetic alone accounts for them is not settled.

Future work should prioritise independent reproduction on other machines and asset versions, larger held-out evaluations that include long and multi-turn contexts, and a more exact account of the compiled program's arithmetic.

\section{Negative results}\label{sec:negative}
%======================================================================

The following approaches were unsuccessful. They are grouped by failure mode, and Table~\ref{tab:neg} states the diagnostic lesson of each group.

Parsing and alignment & forward variants before the gain fix; fixed 128-byte header; numeric layer order; RoPE rescaling & When every variant scores zero, the defect lies upstream of all of them. Check offsets and headers against a known input compiled by the vendor's own tools. \\

\paragraph{Parsing and alignment.} Errors in where and how bytes were read.
\begin{itemize}
\item More than ten forward variants tried before the gain alignment was corrected: Gemma-style $1{+}g$ gains, standard residual, swapped or negated RoPE tables, embedding scales, alternative row stripes, GQA maps, within-vector gain permutations, per-row scale permutations---all 0\% top-1, because the defect was elsewhere.
\item Decoding the 300M model from symbol names, compiled probes and permutation searches: these recover the tile element order exactly but never produce text. The conclusions they suggest---no norm gains ship, the embedding has a lane skew and a 4-row shift, the residual-writing projections hide an unreadable layout, some layers' FFNs ``hurt''---are all consequences of the assumed 128-byte header, the wrong embedding base and the positional $K$/$V$ assignment (Section~\ref{sec:pico}).
\item Reading the 300M adapters' layers in numeric order. Every adapter then appears inert, and the base package's default adapter appears slightly harmful, as a placeholder would. The files follow the manifest's string-sorted tensor names (Section~\ref{sec:pico}).
\item Before the alternating RoPE layout was identified, we attempted to restore spatial understanding with RoPE position rescaling (the RoPE table has 481 rows; $\times10$ or fit-to-480 positions), window-relative positions, other window, group, patch and output orders, cropped position tables, collapsed LLM positions for the image tokens, bidirectional attention over them, rescaled embeddings, no int8 K/V emulation and image-before-question prompts. None helped; each leaves the axis layout unchanged and therefore could not.
\end{itemize}

\paragraph{Runtime and routing.} Wrong assumptions about what the runtime does.
\begin{itemize}
\item Pooled expert routing rules (mean of inputs, of logits, of probabilities; prompt or user turn; prefix mean, vote counts): all below per-token routing, and all wrong---Apple routes from a single token (Section~\ref{sec:runtime}). They appear plausible only under an incorrect prompt template.
\item Routing from the layer-12 FFN input instead of its attention input: 89.4\% teacher-forced, and three times too many experts changed per re-pick (109 versus Apple's 36).
\item A LoRA adapter as the missing component: the Foundation Models API's generic adapter for v11.2 is untrained (B RMS $3\cdot10^{-5}$), so the base model is already what the public API runs. Its ``signature'' (the SHA-256 of the empty string) proves nothing, because the trained feature adapters carry the same one (Section~\ref{sec:adapters}).
\end{itemize}

\paragraph{Uncalibrated measures.} Diagnostics that do not distinguish a defective model from a healthy one.
\begin{itemize}
\item Weight statistics such as ``alignment ratios'' and residual-collapse measures: uncalibrated, and on a healthy model indistinguishable from AFM.
\end{itemize}

\paragraph{Misread references.} Log values that do not measure what they appear to.
\begin{itemize}
\item Apple's \code{MODLM current context $N$ asked to run $K$ tokens} log as an oracle for draft acceptance: it interleaves the guard model, the target and the draft (and several generations) with no stream id, and the draft's catch-up calls are only ever 1 or 3 tokens, so per-step acceptance cannot be read off it. (The \code{SpeculativeDecode} counters can; see Section~\ref{sec:draft}.)
\item Reading Apple's between-prompt expert changes from the cache log: those counts (361--556 of 1012) include cache eviction while the service is idle and do not measure pick differences; only re-picks within one generation do.
\end{itemize}

\paragraph{Execution access.} Attempts to run or alter Apple's programs directly.
\begin{itemize}
\item Running Apple's backbone on the ANE from our own process: the kernel refuses LLM base-model requests from non-platform binaries, even with AMFI disabled.
\item Patching Apple's image encoder to bisect it: a copied MPSGraph package does not load on the Neural Engine. A Core ML replica of our encoder on the Neural Engine was less faithful (0.76) than NumPy (0.987).
\end{itemize}
