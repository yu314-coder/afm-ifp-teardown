\title[Apple's On-Device Foundation Model, Rebuilt]{Apple's On-Device Foundation Model, Rebuilt:\\
A Complete From-Weights Reconstruction of \code{afmplus-v11.2-ifp}\\ (AFM~3 Core Advanced) and a Portable llama.cpp Runtime}
\author{Yu Yao-Hsing}
\email{euler.yu@gmail.com}
\date{November 8, 2026}

\begin{abstract}
We reconstruct Apple's current on-device foundation language model---asset \code{com.apple.fm.language.instruct\_3b.base.generic\_sparse}, display version \code{afmplus-v11.2-ifp}, the model Apple calls \emph{AFM~3 Core Advanced}---entirely from the files Apple Intelligence installs on a Mac, and run it in llama.cpp on any operating system. The model is a 56-layer, 20.3-billion-parameter transformer with a 1536-wide residual stream, 16 query and 8 key/value heads, KV-cache sharing across its last 21 layers, an unusual post-normalised (``x/y'') residual with four learned RMSNorm gains per layer, and an Instruction-Following-Pruned sparse feed-forward network: 23 always-on experts plus 23 of 348 routed experts per token, chosen by a separate router network evaluated once at layer~12. Every 2-bit weight is carried into GGUF \emph{bit-exactly} (55 million spot-checked weights, zero differences); the tokenizer reproduces Apple's own token counts on 81/81 test texts. The two things the model files do not contain---the prompt template and the rule that picks experts---we read out of Apple's inference frameworks: the conversation is rendered as a system turn plus a separate developer turn, and the experts for a whole prompt are chosen from the last prompt token's hidden state and re-chosen every 32 positions. Both are confirmed by Apple's public token counter and by Apple's own runtime log. Against Apple's live model at temperature zero, the reconstruction's next-token choice agrees with Apple's on \textbf{91.7\%} of answer tokens. Nothing in the model is trained or fitted except one input scale factor, to which the results are insensitive.

For most of this project the assembled model predicted nothing. The cause was a single misaligned read: every normalisation gain was taken one element early. We found it with probes \emph{calibrated} on a healthy Apple model---Xcode's on-device code model, whose MPSGraph package we dumped to readable MLIR, executed on the GPU from our own process and reproduced exactly in NumPy. The report documents the model's full structure, the storage formats, the debugging instruments and their calibration, the prompt template and expert schedule recovered from Apple's runtime, the llama.cpp implementation, a standalone converter, every negative result, and what still separates the port from 100\%.
\end{abstract}

\section{Which model is this?}\label{sec:which}

\subsection{The layer: a post-normalised ``x/y'' residual}

Each layer carries four learned RMSNorm gains $g_0,\dots,g_3\in\mathbb{R}^{1536}$. Unlike a pre-norm transformer, both residual additions add \emph{normalised} values:
\begin{align*}
x_L &= \mathrm{rms}(h_{L-1})\odot g_3^{L-1}\qquad(\text{layer 0: } x_0 = k\,e_t + b,\ \text{no norm})\\
h'_L &= x_L + \mathrm{rms}\big(\mathrm{Attn}_L(x_L)\big)\odot g_0^{L}\\
y_L &= \mathrm{rms}(h'_L)\odot g_1^{L}\\
h_L &= y_L + \mathrm{rms}\big(\mathrm{FFN}_L(y_L)\big)\odot g_2^{L}
\end{align*}
with $\mathrm{rms}(v)=v/\sqrt{\mathrm{mean}(v^2)+\varepsilon}$, gains used literally (no $1+g$), and a final output $\mathrm{rms}(\mathrm{rms}(h_{55})\odot g_3^{55})\odot g_\mathrm{out}$ multiplied by the tied embedding. The residual wiring was read from the DMA pattern of the ANE program: the normalised attention input is written to DRAM scratch and read back by the attention residual add; the FFN residual add reads the normalised FFN input. Only this wiring reproduces Apple's outputs (standard residual: 0\% top-1).

\subsection{The Instruction-Following-Pruned feed-forward network}

Sparse layers add two SwiGLU blocks without any gating weights:
\[
\mathrm{FFN}(y)=\underbrace{\sum_{e=0}^{22}\mathrm{SwiGLU}_e(y)}_{\text{always on}}\;+\;\underbrace{\sum_{e\in\mathcal{S}(y)}\mathrm{SwiGLU}_e(y)}_{|\mathcal{S}|=23\text{ routed}},\qquad
\mathrm{SwiGLU}_e(y)=W^{\mathrm{down}}_e\big(\mathrm{SiLU}(W^{\mathrm{gate}}_e y)\odot W^{\mathrm{up}}_e y\big),
\]
each expert being $256$ wide. The ANE program runs the always-on experts from static kernels and the routed experts from a mutable kernel patched at runtime from \code{ifp\_rasterized\_weights.bin}. Both halves matter: the always-on experts alone reach 62.9\% top-1, the routed experts alone 1.4\%, both together 87.5\% (measured with the earlier template).

\paragraph{When experts are chosen.} Apple's runtime does not route per token. It runs the dense layers over the whole prompt, takes the layer-12 input of the \emph{last} prompt token, runs the router once, and uses that expert set for every prompt token and for generation; it re-picks from the current token only at absolute positions that are multiples of 32. Section~\ref{sec:runtime} shows how this was read out of Apple's inference framework.

\caption{The 2-bit weight unit. A projection is split across the 16 ANE units bank-cyclically; a chunk with more banks holds the lower bank slots. The value of a weight is $w = s_m\,(c-1.5)$ with $c\in\{0,1,2,3\}$ and $s_m$ the fp16 row scale. Experts in \code{ifp\_rasterized\_weights.bin} use the same codes with a simpler order: code $p\mapsto$ (row $16\lfloor p/(16\,\mathrm{in})\rfloor + p\bmod 16$, input $\lfloor p/16\rfloor \bmod \mathrm{in}$).}\label{fig:tile}
\end{figure}

\paragraph{Exact GGUF encoding.} llama.cpp's Q2\_K stores, per 256 weights, sixteen 4-bit sub-block scales $\mathit{sc}$ and mins $m$, a super-scale $d$ and super-min $d_{\min}$, and evaluates $w = d\,\mathit{sc}\,c - d_{\min}\,m$. Choosing $\mathit{sc}=2$, $m=3$ and $d=d_{\min}=s/2$ gives
\[
w = \tfrac{s}{2}\cdot2c-\tfrac{s}{2}\cdot3 = s\,(c-1.5),
\]
and halving an fp16 number is exact (barring underflow, which never occurs here). The int4 embedding ($w=s_t\,q$, $q\in[-7,7]$, per-token fp16 scale $s_t$) maps exactly onto Q4\_0 with $d=s_t$ and nibble $q+8$. Dequantising the GGUF with gguf-py reproduces Apple's weights with maximum absolute difference 0.

\paragraph{Layout facts and how they were ground-truthed.} We compiled known weights through Apple's own ANE compiler (\code{mil\_to\_hwx -a h16}) and decoded the result: the output axis is the bank-cyclic stripe above, the input axis is natural, the codebook and row scales are as in Figure~\ref{fig:tile}, and constants (gains, biases) are stored in natural order. A calibrated copy-circuit probe (Section~\ref{sec:validate}) independently confirms the stripe, the head order and the V/O pairing: every alternative layout scores at chance.

\begin{finding}
The earlier parse located the table by statistical signatures and accepted a start two bytes early. Every RMSNorm therefore multiplied channel $r$ by the gain of channel $r{-}1$. Because $g_0$ and $g_2$ are zero-centred, this flipped the sign of about a third of every residual write at every layer, and the assembled model predicted nothing (0\% top-1, no induction).
\end{finding}

\paragraph{How it was found.} Nothing looked wrong in isolation: each tensor was correctly laid out and correctly paired. The breakthrough was calibrating probes on a healthy Apple model and then comparing \emph{reader--reader} with \emph{reader--writer} relations. In AFM, query--key and gate--up relations were as healthy as in CodeLM, but value--output (copy heads) and up--down (FFN neuron coupling) relations were weak. In a trained network, the sign of the coupling between up-row $i$ and down-column $i$ agrees with the sign of the gain that scales the write. In AFM the \emph{number} of negatively coupled channels equalled the number of negative entries of $g_2$ in every layer---while their \emph{positions} disagreed (Figure~\ref{fig:offbyone}, left). Matching each channel's 11-layer sign signature against the table gave a constant offset of one element. Read aligned, the agreement rises to 98--99.9\% (right) and the model works: 66\% top-1 against Apple's outputs on the first attempt, rising to 87.5\% with the llama.cpp port and exact tokenization.

Right: per-channel sign agreement after reading the table aligned; a one-element shift gives chance level. Layer 0 is the exception because its input is the raw embedding.}\label{fig:offbyone}

\section{Validation instruments and their calibration}\label{sec:validate}
%======================================================================

\paragraph{The oracle.} \code{afm -t 0} (a small Swift wrapper around the Foundation Models API) produces Apple's greedy answers; at temperature zero, Apple's top-1 token at every answer position is the next token, so teacher-forced top-1 agreement is an absolute measure. We use 40 prompts (1127 answer tokens). The API exposes no probabilities.

\paragraph{A healthy reference: CodeLM v3.} Xcode's on-device code model ships as a GPU MPSGraph package. Its MLIR (via \code{-getIR}) is a complete, readable tamm transformer---pre-norm, standard residual, RoPE then QK-norm, SwiGLU, KV reuse from layer 34, int4 weights with group-32 scales---with the same backbone shape as Apple's other 3B-class models (56 layers, 35 KV-owning, 2048 wide, 16/2 heads). We ran it on the GPU from our own process through \code{MPSGraphExecutable} (100\% induction accuracy) and reproduced its logits in NumPy exactly (correlation 1.00000, 100\% argmax agreement). Its tokenizer and embeddings are unrelated to v7-3b's, so it cannot donate weights---but it calibrates instruments.

\paragraph{What the calibration showed.}
\begin{itemize}
\item \emph{Zero-centred literal gains are normal} in tamm (CodeLM's pre-attention gain: mean $+0.003$, 46\% negative).
\item \emph{The embedding--weight ``alignment ratio'' used for months is not diagnostic}: a healthy model scores the same (1.0--1.4).
\item \emph{The OV copy probe is diagnostic}: CodeLM has several heads that map a token to itself at rank 0--16, even after naive 2-bit rounding; decoded AFM had none below rank 1000 (Figure~\ref{fig:copy}). Every alternative V/O layout scored at chance, which ruled out layout errors and pointed at the gains.
\item \emph{The same-token QK probe} found AFM's query--key circuits healthy (rank-0 heads) and confirmed the head pairing $h\mapsto\lfloor h/2\rfloor$.
\end{itemize}

\begin{figure}[h]
\centering
\includegraphics[width=\linewidth]{figs/fig_copy.pdf}
\caption{Copy-circuit probe: for each layer, the best attention head's median rank of the input token in $E\,W_O W_V\,e_t$. Healthy CodeLM has rank-0 heads; AFM's raw $W_OW_V$ peaks at weak copying because in AFM the write passes through the signed gain $g_0$, whose positions were scrambled by the table shift.}\label{fig:copy}
\end{figure}

\paragraph{Apple's int8 calibration as a ground truth.} The ANE program stores per-layer scales for its int8 K/V cache. Apple chose them from real activations, so they bound the true magnitudes. With the corrected gains, the reconstruction's values stay inside Apple's ranges, and its keys stay inside up to the 99.9th percentile; only the most extreme 0.1\% of keys would clip (Figure~\ref{fig:kv}). This is an independent check of the internal scales, including the input embedding scale.

\section{What Apple's runtime does: the prompt and the expert schedule}\label{sec:runtime}
%======================================================================

Two things the model files do not contain decide what the model sees and which experts it uses: the prompt template (the metadata only names it, \code{afm\_cider\_v2}) and the rule for choosing experts. Both live in code, in two private frameworks of the dyld shared cache: \code{TokenGenerationCore} renders and tokenizes prompts, \code{TokenGenerationInference} drives the model. \code{dyld\_info -disassemble} prints both with Swift symbol names. One detail matters for reading them: Swift stores string literals of up to 15 bytes inside the instruction stream (\code{mov}/\code{movk} immediates), so \code{<start\_of\_turn>} and friends never show up in a strings dump.

\subsection{The prompt template}
\code{PromptPreprocessingTemplateAfmCiderV2Convention} takes its special-token table from the older Cider~v1 convention and overrides only audio and reasoning entries. Decoding the immediates gives turn start \code{<start\_of\_turn>}, turn end \code{<end\_of\_turn>}, and roles \code{system\textbackslash n}, \code{developer\textbackslash n}, \code{user\textbackslash n}, \code{model\textbackslash n}; the ``thought budget: none'' and ``developer static instructions'' entries are empty. Its \code{cacheableSystemPrefix} concatenates
turnStart, the system role with Apple's default instructions, the thought budget, turnEnd, a newline, then turnStart and the developer role. A FoundationModels conversation therefore renders as
\begin{center}\small
\code{<bos><start\_of\_turn>system\textbackslash n}\emph{default}\code{<end\_of\_turn>\textbackslash n}\\
\code{<start\_of\_turn>developer\textbackslash n}\emph{instructions}\code{\textbackslash n<end\_of\_turn>\textbackslash n}\\
\code{<start\_of\_turn>user\textbackslash n}\emph{prompt}\code{<end\_of\_turn>\textbackslash n<start\_of\_turn>model\textbackslash n}
\end{center}
where \emph{default} is the \code{systemInstructions.default} text of the adapter metadata (``A conversation between a user and a helpful assistant. You are a foundation model developed by Apple. \ldots'') and the developer turn holds the app's instructions. The public API verifies every detail: \code{SystemLanguageModel.tokenCount(for:)} accepts transcript entries and returns the length of the rendered prompt, which equals the length the inference service logs (``asked to run 71 tokens'') for the same conversation. Table~\ref{tab:tc} compares it with our rendering. Our earlier template folded everything into one system turn and omitted the instructions our reference CLI passes; with the exact template, teacher-forced agreement rose from 87.5\% to 90.5\% and the first answer token from 30 to 38 of 40.

\subsection{The expert schedule}
The inference log of a single request already shows the shape of the algorithm: a ``prompt expert compute function'' (\code{lora\_48\_ifp3\_r48\_prompt\_opt\_dense\_only\_256\_64}, the dense layers only) runs over all prompt tokens, then ``Picking IFP experts at position=70 isPromptPick=true'' for a 71-token prompt, then the sparse layers run over the \emph{whole} prompt again with the picked experts. The dense-only function returns a \code{1536}$\times$\code{64} fp16 tensor per 64-token chunk, one column per token. In \code{TokenGenerationInference}, \code{computePromptExpertState} builds the router input with \code{IFPDenseLayerOutput.makeExpertsTensor(tokenIndex:)}, whose loop copies the 1536 values of a single column into a $1536\times1$ tensor---no mean, no accumulation. The router (\code{project\_experts}, the network of Figure~\ref{fig:ifp}) then yields the top-23 experts per sparse layer. During generation, \code{repickExpertsAtBoundary} calls the same picker, and \code{IFPExpertPicker} rejects any intermediate pick whose position is not a multiple of \code{expert\_selection\_frequency} (an \code{sdiv}/\code{msub} remainder test against 32). With prompt length $P$, token $t$ therefore uses the experts chosen from $x_{12}$ at
\[
s(t)=\max\!\big(P-1,\;32\lfloor t/32\rfloor\big),
\]
so every prompt token uses the last prompt token's choice. Averaging the prompt instead is clearly wrong (79.3\% teacher-forced), while the single-token rule beats per-token routing (Section~\ref{sec:fidelity}).

\paragraph{An outside check of the router.} Each pick also logs \code{CacheExpertExpertCache: \ldots\ replaced=}$n$, the number of (layer, expert) choices that changed. We ran six long generations on Apple's model, collected its 47 re-picks, replayed the same token sequences through our model and counted how many of our choices change at the same positions. With the single-token rule on the layer-12 attention input the two series agree closely (Figure~\ref{fig:repick}: mean 26.7 versus 27.1 experts, correlation 0.84); prefix means correlate at 0.21--0.53 and the FFN-input variant changes three times too many. This validates the router input, the router network and the rule independently of any answer text.

\section{The llama.cpp implementation}\label{sec:llama}
%======================================================================

The fork adds one architecture, \code{afm}, in \code{src/models/afm.cpp} (about 180 lines), plus three supporting changes.
\begin{itemize}
\item \textbf{Graph.} Layer 0 adds the scaled embedding and bias; each later layer normalises the previous output with $g_3$; queries and keys use \code{rms\_norm}, NEOX RoPE, then a gain multiply; the residuals follow Figure~\ref{fig:layer}. Sparse layers run the always-on experts as a ``shared expert'' SwiGLU of width 5888 and the routed experts with \code{mul\_mat\_id}, summed by one row reduction with no weights. The router network lives on layer 12 and its logits are sliced per layer. The output applies the double norm and the tied embedding.
\item \textbf{KV reuse.} Layers 35--55 call attention with null K/V, and the cache maps them to layer 34. This needed a two-line fix in the non-sliding-window attention path, which assumed K/V were always present.
\item \textbf{Metal kernels.} Metal's batched expert matmul is instantiated for specific experts-per-token counts; we added 14 and 23 (ifp2, ifp3). CUDA uses a generic path for such counts, and Vulkan supports Q2\_K expert matmuls, so no change is needed there.
\item \textbf{Apple's expert schedule.} The router's logits for each sequence persist in a small device buffer (64 sequence slots) owned by the model. A custom graph input computes, per micro-batch on the host, which logits every token uses: a run of several tokens of one sequence is a prompt chunk and takes its last token's logits, which are stored; a single decode token re-picks only when its position is a multiple of 32 and otherwise reads the stored choice. Because the indices are data rather than graph structure, llama.cpp's graph reuse and multi-sequence batching stay correct. \code{AFM\_ROUTE\_TOKEN=1} restores per-token routing.
\item \textbf{int8 KV emulation.} The GGUF carries Apple's per-layer K/V scales; keys and values are rounded and saturated to int8 before caching. Rounding uses the fp32 magic constant $1.5\cdot2^{23}$, because \code{ggml\_round} misbehaved on Metal.
\end{itemize}
On an M4 the model processes prompts at about 150 tokens/s and generates 12--21 tokens/s. The patch applies to upstream llama.cpp (commit \code{41ea261}); the repository's workflow builds Windows (CPU, Vulkan, CUDA), Linux (CPU, Vulkan) and macOS (Metal) binaries from it.

\section{What did not work}\label{sec:negative}
%======================================================================

Recorded so that nobody repeats them:
\begin{itemize}
\item Running Apple's backbone on the ANE from our own process: the kernel refuses LLM base-model requests from non-platform binaries, even with AMFI disabled.
\item Ten-plus forward variants before the gain fix: Gemma-style $1{+}g$ gains, standard residual, swapped or negated RoPE tables, embedding scales, alternative row stripes, GQA maps, within-vector gain permutations, per-row scale permutations---all 0\% top-1, because the defect was elsewhere.
\item LoRA: the base model's adapters are untrained, and the Foundation Models API's generic adapter for v11.2 is empty (its signature is the SHA-256 of the empty string).
\item Weight statistics such as ``alignment ratios'' and residual-collapse measures: uncalibrated, and on a healthy model indistinguishable from AFM.
\item Pooled expert routing rules (mean of inputs, of logits, of probabilities; prompt or user turn; prefix mean, vote counts): all below per-token routing, and all wrong---Apple routes from a single token (Section~\ref{sec:runtime}). They had looked plausible only because our template was wrong.
\item Routing from the layer-12 FFN input instead of its attention input: 89.4\% teacher-forced, and three times too many experts changed per re-pick (109 versus Apple's 36).
\item Reading Apple's between-prompt expert changes from the cache log: those counts (361--556 of 1012) include cache eviction while the service is idle and do not measure pick differences; only re-picks within one generation do.
\end{itemize}

%======================================================================
\section{Toward 100\%}\label{sec:open}
%======================================================================

The prompt template and the expert schedule, the two open items of earlier drafts, are now Apple's own (Section~\ref{sec:runtime}). What remains is numerical:
\begin{enumerate}
\item \textbf{Numerics.} The ANE computes in fp16 with a lookup-table SiLU and its own accumulation order; we emulate only the int8 KV cache. The re-pick comparison (Figure~\ref{fig:repick}) quantifies the effect on routing: our router changes about as many experts as Apple's at each boundary, but individual picks differ by a few experts in 1012.
\item \textbf{The input embedding scale} $k$ is the one constant not read from Apple's files: the embedding gather in the ODIE program has no multiply, so it is folded into the first ANE stage. It is fitted; Section~\ref{sec:fidelity} shows the agreement as a function of $k$.
\end{enumerate}
Every weight, gain, bias, the router, the tokenizer, the template and the routing rule come from Apple's files and code; nothing was trained or fine-tuned.
